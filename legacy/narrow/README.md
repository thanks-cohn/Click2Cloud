# Legacy Narrow — exact trie semantics and alias pitfalls

**Actual source:** [REDOWN V3 Narrow and validator](https://github.com/thanks-cohn/REDOWN/blob/5041b5763541812c505c9cde6e8f79cb23a7b193/extension/right-click-v3.js#L1-L70), [audited duplicate/alias casebook](https://github.com/thanks-cohn/REDOWN/blob/94a1a5f0699eec904d989a3823d22f9bf2bd131d/FOREVER_WORKS/v3-plus-one-master-audit/04_DUPLICATES_ALIASES_AND_BRANCH_INSTANCES.md), [Narrow desired contract](https://github.com/thanks-cohn/REDOWN/blob/5041b5763541812c505c9cde6e8f79cb23a7b193/FOREVER_WORKS/v3/P0_MENU_MODE_RECONSTRUCTION_CONTRACT.md). **New owner contract:** [Narrow picker proposal](../../narrow/rewrite_proposition/LOCATION_PICKER_CONTRACT.md).

## Mechanisms worth preserving

- **Real ancestry from exact prefix segments.** V3 groups destinations by exact `(profileId,accountId,bucketName)`; builds a separate per-scope path trie by literal `/` segments. Shared ancestors render once. Names are case-sensitive and Unicode-preserved; do not derive target keys from edited menu titles or normalize case.
- **Synthetic parent = navigation, not a save.** If `Art/Photography/Weddings` is selected but `Art` isn't, `Art` remains a visible branch only. No implicit save permission is conferred on an ancestor. Exact selected destination leaves are save actions.
- **Selected parent with selected children.** When a configured destination also has visible children, V3 emits an explicit `<id>:send` `Save here` child so users can save to the parent, not just descendants. New Narrow must retain this path-to-action property.
- **Multiple saved aliases at the same exact location.** V3 turns their path node into a navigation branch and exposes each saved alias as a separate action with its own destination ID. This is especially important with the owner's permission for **two identical visible names AND same path**. Do not collapse action IDs when coalescing parent navigation.
- **Explicit parentId is not visual ancestry.** V3 uses `parentId` for validation, eligibility, editor nesting and cascading deletion; natural path segments build the displayed hierarchy. A disabled explicit parent invalidates children linked through it, while an independently configured child under the same prefix may remain eligible. New mode-independent editor needs a reviewed migration policy before discarding parentId.
- **Ordering is not alphabetic.** Trie group and sibling order reflects original configured record order/first insertion; label editing should not randomly reorder destinations or create orphaned `Save here` actions. Parent-first and structurally valid ordering remains essential.
- **Scope collision guard.** Identically named `photos` buckets in two accounts need distinct headings/accessible scopes even if their human labels match; no cross-account union by bucket name.

## Gaps in current new proposals

1. **Terminal duplicate labels in one Narrow path may collide visually, not technically.** Two saves named `Wedding` under the same selected folder need two distinct terminal native leaves with distinct IDs. The new manager model tests saved IDs, but the **real Narrow menu compiler** must prove two actions are emitted and each resolves exact target. Same visible labels are owner-approved: no blocking duplicate popup.
2. **A selected parent and selected grandchild need a concrete compiler test.** The current Narrow draft describes a full branch/last label but not detailed `Save here` action generation at every selected intermediate node and root.
3. **Alternate whole branch instances remain a separate advanced problem.** V3 coalesces same physical path into one ancestry branch. Earlier owner requests allowed distinct *named whole branches* pointing at the same physical path. That requires separate presentation branch instance IDs, **not** cloning provider folders or treating a display alias as a location ID. Preserve as an OPEN future feature; do not complicate the minimalist navigator unless explicitly chosen.
4. **Migration dedup hazard.** Old `migrate()` may drop records with same `profileId,prefix,label` even if they had distinct IDs. An owner's new duplicate-ID-safe model must retain all original records wherever recoverable, with provenance and a documented non-destructive migration. Distinct source IDs never collapse merely because path/title matches.
5. **Root alias and hidden ancestors.** A root alias `prefix:''` should not disappear because Simple has a default. Old Narrow remains capable of displaying it; new per-mode root behavior must be explicitly verified. Keep source `enabled=false`/ancestor semantics out of a global cross-mode flag.
6. **Mode selection shouldn't cross-write.** V3 had one destination array for Simple and Narrow. New Narrow owns its own alias/selection revision. The shared tree picker can emit an intent to Narrow; no Simple state write or accidental active-mode switch is permitted.
7. **Native budget and partial branches.** If a branch requires a parent + `Save here` + children, reserve those structural entries as a unit; truncating mid-branch can emit unusable or invisible orphaned saves. Preserve a discoverable `More destinations` or equivalent, not silent loss.
