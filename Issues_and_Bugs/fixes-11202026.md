## 2. File Explorer — blank right-hand file area when logged out

### Owner-observed problem

While **not logged in**, the right-hand File Explorer file-content area shows redundant empty/error text such as:

```text
Reconnect to browse. Saved locations are preserved. · Use Refresh to retry.
0 items
Reconnect to browse. Saved locations are preserved.
```

This makes an unauthenticated File Explorer look cluttered and as though a folder listing or retry is active.

### Requested future fix

- When the Cloudflare account is **logged out/disconnected**, the **right-hand file listing area should be visually blank**. Do not show that reconnect message, its duplicate, a `0 items` counter, a misleading file-grid empty state, or a Refresh-to-retry prompt in this pane.
- This also applies to a clearly unauthenticated/reconnect-required state, including when the Shelf opens before an account has been authenticated. An unknown/checking status must not be presented as a confirmed empty folder.
- Keep the **Log In** action available in the appropriate File Explorer connection/navigation UI **outside the right-hand file area**, as already specified by the current Explorer login UX. Do not replace the blank content pane with a large login message.
- After successful login and authorized folder selection, resume normal file listing, counts, loading feedback, and legitimate empty-folder messages.
- Do **not** suppress genuine connected-state listing errors, failed cloud reads, or important status/diagnostic information. Those must remain available in appropriate status/diagnostics UI; only the unauthenticated right-hand file area should be blank.
- Do not delete or clear persisted saved destinations, default locations, folder preferences, receipts, or user data. Sign-out must not be treated as an empty or freshly initialized configuration.
- Avoid a fleeting stale `0 items` caption or duplicated reconnect message during sign-out, reconnect, or initial Shelf boot.

### Source location (for implementation audit)

- `extension/app.mjs` → `connections()` and `enterExplorer()` can set `listingError = 'Reconnect to browse. Saved locations are preserved.'` on disconnect/reconnect-required cases.
- `extension/app.mjs` → `renderFiles()` currently falls back to displaying `listingError + ' · Use Refresh to retry.'` in `.empty`.
- `extension/app.mjs` → `renderListingCaption()` currently emits a file count such as `${entries.length} items` independently of authenticated-state presentation; `#listing-state` may show a second listing error.
- Apply a deliberate connection-aware **rendering** rule instead of wiping canonical saved locations or falsifying storage state.

### Acceptance

1. Fresh unauthenticated Shelf → File Explorer: right file area blank, no `0 items`, no reconnect text, no fake folder contents; Log In remains discoverable elsewhere.
2. Authenticated Explorer → sign out: right file area becomes blank without duplicate captions or a transient misleading count.
3. Reconnect successfully: verified listing and legitimate counts resume normally; previously saved destinations remain available.
4. Authenticated but listing fails: show a truthful error in the appropriate UI rather than silently hiding a real provider problem.
5. Confirm behavior in Minimal and Remote V1, across compact and expanded Shelf widths, without disturbing the folder tree, authentication, or normal saving.

## 5. History should live-update when right-click saves and screenshots finish

**Owner request:** When a **new image** is saved through **Chrome's right-click Save menu** or the **screenshot-to-cloud feature**, it should appear in **History in near real time** while History is open, without the user navigating away, re-opening History, clicking Refresh or reloading the Shelf.

### Requested future behavior

- For an ordinary native right-click image save, update History as soon as the new authoritative result/receipt is durably recorded. Show the filename, source/target, timestamp and a truthful status (pending, verified, partial or unconfirmed/failed). If the save progresses from pending to verified, update the **same** operation entry rather than adding duplicates.
- For screenshot captures, update History as the capture/upload result becomes available and whenever durable receipt state changes, including **multi-destination** outputs. Keep **one capture entry, one shared preview**, independent GO TO and URLs cards for each destination, and accurate per-output verification counts.
- Image preview must appear when a real saved image can be read and the preview is requested/visible. Never imply that a save succeeded merely because the capture or right-click operation was initiated. Continue using authenticated R2 reads for verified screenshot previews; do not create duplicate cloud objects or repeat captures merely to update History.
- If History is **currently visible**, show the change promptly without refresh. If it is not visible or the Shelf is closed, retain the durable result normally, and read the latest entries the next time History opens. New notifications are not required; respect the quiet-screenshot preference.
- Where History has date-grouping, pagination, display filters, search/expanded rows, scrolling and lazy thumbnails, preserve the user's current view where sensible. Avoid repeatedly redrawing a huge lifetime History tree for each progress event; debounce/coalesce bursts and make incremental updates or a bounded refresh that preserves UI interaction state.
- Avoid duplicate entries or stale/regressing states during repeated messages, retries, service-worker restarts, Shelf reconnects, and multiple open windows. Use stable operationId and capture/output IDs plus persisted revision/receipt semantics; re-read authoritative durable results rather than trusting a transient event as proof.
- Network/authorization errors remain truthful; do not clear saved History or disclose private credentials/URLs in a UI event. Historical records and normal export remain intact.

### Source hints (existing partial behavior; do not assume feature completely absent)

- `extension/background.mjs` → `recordRemote()` already persists `current.recordRemoteResult(value)` then sends a `chrome.runtime.sendMessage({channel:'remote-result',result:...})` event for ordinary remote saves. Audit whether the Shelf's History view listens for **this event** and refreshes it; it may currently be handled only as feedback elsewhere.
- `extension/screenshot-background.mjs` sends `channel:'screenshot-result'` messages with a `recorded` flag. `extension/app.mjs` already calls `historyUI.load()` when `view==='history' && message.recorded`. Verify this is correct for every screenshot completion/partial/retry and when History is actually mounted; investigate why user-visible refresh may still be late or missing rather than adding duplicate event listeners.
- `extension/history-page.mjs` `createHistoryPage()` exposes `load()`; today it retrieves History preferences and pages of durable results and re-renders. Avoid concurrent full reloads, racing `stop()` calls, loss of expanded state/scroll/focus, repeated image loading, and heavy CPU cost during bursts.
- Investigate event delivery across MV3 service-worker lifecycle and running vs closed Shelf; when an event is missed, the next History open must reconcile against the persisted records, not depend on an in-memory notification.

### Acceptance

1. Keep History open, right-click Save an image from a normal webpage: the resulting new save appears automatically and changes status on confirmed verification (no page navigation/manual refresh).
2. Keep History open, capture a screenshot using Alt+Q and separately Ctrl+Shift+Y: each newly recorded capture appears promptly with correct shared image and destination output cards; 3 destinations yield 1 entry/preview and 3 output cards, not 3 captures.
3. Run many saves rapidly: no missing/duplicate rows, no frozen History, no lost expansion/scroll focus, and verified outcomes remain truthful.
4. Retry an unconfirmed save or screenshot: update its existing receipt, preserving operation/output identity. Simulate sign-out/permission failure and failed verification without false success.
5. With History closed, reopen after new saves and after an MV3 worker restart: all durable records appear, with correct filters/pagination. Save engines, receipts, screenshot shortcuts, and quiet notifications remain unchanged.

**Status:** OPEN — future reliability/UX improvement; investigate existing partial real-time behavior first. Documentation only.

## 7. REDOWN-simple custom-domain connection — hostname only; no Zone ID field

**Owner directive (November 20, 2026):** Make **Click2Cloud as simple as REDOWN** for connecting a domain. The user should **only type their custom domain and click Connect domain — DONE**. No manual Cloudflare Zone ID, extra form, copy/paste of internal identifiers, confusing second setup workflow, or unnecessary Recheck to see the result.

### Desired UX

1. History → URLs → **Custom domain** accepts a single hostname, e.g. `assets.example.com`.
2. User clicks **Connect domain**. Where domain connection will make bucket contents publicly reachable, retain a concise, explicit disclosure/confirmation of that security impact; avoid asking for technical identifiers.
3. Click2Cloud resolves any Cloudflare zone information **behind the scenes** for the currently authenticated account and verifies that the matching zone is actually accessible and is valid for the exact bucket's account.
4. If already connected, report that result and show the actual configured domain/file URL immediately. Otherwise perform the authorized direct R2 custom-domain connection, read back the association, and automatically show the real, exact-file public URL **in the same History URLs section** once Cloudflare confirms it. Distinguish connected/configured from fully active SSL/DNS or independently verified anonymous reachability; never say Done if unverified.
5. Show compact progress and human-readable failure states without forcing users to leave History or manually refresh. Preserve the previous section's separate, single-line **Cloudflare domain setup** link directly below the button.
6. If Cloudflare doesn't expose the necessary zone through the current authorized account, say clearly **“This domain isn't available in the connected Cloudflare account”** or **“Cloudflare permission is needed to find this domain”**, with a helpful route to Cloudflare setup/login. **Do not expose a Zone ID field as a fallback**. Do not assume merely possessing a Zone ID grants cross-account access. If an additional scoped OAuth permission is essential, request explicit authorization through the normal, trusted OAuth process; do not silently broaden grants.

### Why this needs a real implementation change

- **REDOWN reference:** `thanks-cohn/REDOWN/extension/options.js` `assetCorsControl()` asks for a hostname and a single **Use domain** click; `extension/background.js` `configureAssetDomain()` uses the Workers custom-domain association API `PUT /accounts/{accountId}/workers/domains`, then GET readback. REDOWN's Worker-based `/assets/` URL route is not the same as a direct R2 custom-domain mapping.
- **Current Click2Cloud:** `extension/history-destination-urls.mjs` currently reveals an explicit `Cloudflare Zone ID` field on `CUSTOM_DOMAIN_ZONE_REQUIRED`; `src/cloudflare/r2-public-domains.mjs` `connectCustomDomain()` only finds `knownZone` from *already listed custom domains on the bucket*, then otherwise requires a 32-character `zoneId` parameter for its **direct R2** POST. New domains typically have no such existing association, so this auto-detection path is insufficient.
- **Implementation direction:** Discover the owning Cloudflare zone automatically through a properly authorized, account-scoped Cloudflare zone lookup. Match the **longest applicable hostname suffix** and exact account/zone identity; reject ambiguity and wrong-account zones. Use the discovered zone ID internally for the existing R2 POST and verify with independent GET readback. Keep endpoint/auth transport scoped and account-fenced. Do not silently swap direct-R2 delivery for REDOWN's Worker proxy or reuse REDOWN's `/assets/` paths, unless an independently approved product design explicitly changes the delivery model.
- Preserve existing development URL (`r2.dev`), all custom domains, stable exact-file object-key URL encoding, receipts, screenshot History outputs, source-based Get URL and cloud permission protections. **Do not trigger any domain or bucket mutation simply by opening History or Get URL.**

### Acceptance tests

- **Happy path:** domain already in the connected Cloudflare account but not on the bucket → enter hostname, click Connect (plus clear exposure consent if needed) → automatically resolve zone, attach direct R2 domain, GET readback, show exact-file URL without Zone ID input or extra Recheck.
- **Existing domain:** already connected domain → no duplicate POST; verify and show URL automatically.
- **Wrong account / absent domain / zone lookup forbidden:** simple actionable explanation, **no Zone ID field**, no unauthorized POST, no invented URL or success.
- **Pending activation:** show truthful pending state with automatic bounded refresh where appropriate, no false verified public reachability.
- **Multiple domains, longer/specific matching zone, stale selection, sign-out mid-request, repeated clicks, duplicate requests, and different destination buckets:** no cross-account or wrong-bucket mutation.
- Run focused fixture tests plus installed Chrome UX verification. Document missing permission or real-provider blockers separately; never claim the user-friendly flow works merely because the form was hidden.

**Status:** OPEN — future implementation only. This entry does not change Cloudflare integration or current extension code.
