# REDOWN 0.3.32.4 — configurable timed campaigns, visible Queue and History, robust fixture coverage

Base: 0.3.32.3 / 3e8c242db9a72006e486ed6b59b46190a0b0d4a2. Preserve proven Windows source-repair behavior, existing UI themes and production upload APIs. Use the real shared upload, download, queue and history pathways; no alternate simulated success engine.

## P0: time-budgeted campaign
- Primary owner workflow (P0): after normal sign-in, explicit QA pairing/authorization and one-time setup, the operator drops files/folders into the default input directory and runs ONE documented Python CLI command (or a short Python entry point) to automatically inventory, hash, resolve the workload, preflight, execute, and generate receipts. No manual directory batching, separate manifest creation, validate/run chains, fresh manifest naming, or repeated pairing between internal batches. Support optional explicit manifests and separate dry-run/validate commands for advanced use; keep existing commands compatible. Default simple live workflow is upload-only with production confirmation and no mandatory independent readback or retained download. Explicitly selected verification, download-only and round-trip remain available. Provide an easy input/output configuration and a Python-callable shared interface if practical, not a second engine. Live writes must be explicitly requested and covered by the existing approved target and cost/resource budget; print the effective destination, mode, duration and budgets, and request additional approval only if necessary. No silent provider scope expansion.
- Automatically allocate unique campaign/run/receipt identifiers, persist the resolved plan before the first mutation, and emit durable per-file receipt entries immediately after each outcome, not only at the end. Print receipt paths and concise live progress in CMD; atomically checkpoint summary counts and publish the final JSON/NDJSON and readable summary as soon as the run completes or its time/authorization/resource window ends. Preserve receipts on exceptions, cancellation, browser disconnect and restart. No false success, no plaintext secrets, and no dependence on an open Settings page. The same input can be used for a deliberately new campaign; interrupted campaigns continue through an explicit continuation action with no replay of completed operations.
- Remove/replace the current arbitrary fixed ceilings that prevent the immediate 2,000-file workload: audit and coordinate CLI/manifest/schema, native relay and frame limits, browser bridge/OPFS staging, production local-upload service (currently two active uploads), authorization grant (currently 250 file slots, 8,192 provider call units, 640 MiB modeled traffic), operation planner (currently 1,500 operations), and per-file/spool (currently 8 MiB) limits. Replace artificial per-campaign count/traffic ceilings with configurable approved budgets and bounded incremental admission; never simply disable security/resource safeguards, provider rate/size restrictions, framing protections or authorization boundaries. Keep physical concurrency and working-set limits explicit and measured, queue excess work rather than rejecting it with RESOURCE_BUSY, reserve capacity/fairness for ordinary product operations, and avoid whole-campaign reservation that rejects valid inventories larger than one window's capacity. Preserve current proven transport/Windows source identity. Show actual remaining time, approved file/byte/request/cost budgets, throughput and blockers. A campaign can contain more work than its current window can finish; unadmitted work remains pending for continuation, not failed. A user-approved session duration must be sufficient for the intended benchmark or clearly report the earlier effective deadline; do not assume OAuth has a fixed lifetime.
- Keep the simple workflow compatible with older upload-only manifests which explicitly or historically require independent readback: preserve their verification contract, and make operation direction, verification level and local retention independently configurable where compatible. New simple upload-only path must not add an independent download by default. Folder preview eligibility uses production-confirmed uploads and existing metadata, with safe lazy preview on user expansion; it must never cause mandatory lab readback or background downloads during a pure upload benchmark. Distinguish production verification and independent laboratory verification in persistent status, counts and History, including later uncertain results.

- Immediate release target: support a campaign inventory of at least 2,000 files and aim to complete at least 2,000 files within the default 40-minute authorized window on a representative small-file workload, continuing beyond 2,000 for as long as the configured time, available authorization, and approved resource budgets allow. Do not treat 2,000 as a maximum or a mandatory minimum for every user workload. Report upload-only, download-only and round-trip performance separately; do not claim the 2,000-completed target passed unless actually measured in that mode with representative fixtures and correct evidence. Large-file/mixed workloads may have lower counts; report actual results, bottlenecks and verification levels. If the target is not met, identify the remaining work rather than weakening verification or overstating readiness.
- Future architectural target: design the scheduler, manifests, persistent operation records, bounded streaming, pagination, receipt storage, authorization budgets and UI to scale toward 10,000+ files without structural redesign. A successful 10,000-file live run is NOT required for this implementation or Codex handoff. Do not spend the current session chasing speculative large-scale optimization or implementing all future capacity tiers. Validate architecture with focused offline/resource-bound tests and the immediate 2,000-file acceptance path; document remaining limits and future scaling steps. Keep inventory capacity separate from per-window admission budgets; accept a larger valid inventory when supported and process only eligible work within the approved window, preserving the remainder for continuation. No fixed 2,000-file ceiling in the architecture.
- Benchmark duration is user-configurable, NOT hardcoded. Default to 40 minutes (2400 seconds) initially. Add a persisted editable default in Python Laboratory Settings and a per-campaign manifest duration override; reuse the existing duration/limit schema where possible. Explicit manifest duration takes precedence over the Settings default; display and freeze the resolved duration in preflight and the approved run plan. Legacy manifests retain their explicitly declared durations. Validate positive finite durations against supported resource and authorization limits, explain any blocker, and never silently extend a grant or shorten a requested window. Session authorization duration is a separate setting; do not assume Cloudflare OAuth itself has a 40-minute lifetime or silently renew authority; the effective dispatch deadline is the earlier of the authorized deadline and benchmark deadline. Allow shorter or longer user-selected windows when authorized, with proportional/measured drain headroom rather than fixed minute markers. A duration change applies to a future window, never retroactively changes an active or completed benchmark. Renewal does not restart its clock; a later continuation window gets its own receipt and contributes to cumulative campaign totals. Include configurable duration, default/override precedence, deadline and renewal tests.
- Workload modes are first-class and independently selectable: upload-only, download-only, or round-trip (both). No mandatory download leg, independent content readback, or saved local download for upload-only mode. Use existing CLI operation selection where possible and preserve backwards compatibility. Upload-only success requires existing production publication evidence, source identity and receipt; any optional independent readback is a separately declared operation, never an implicit full download. Download-only uses an explicitly approved existing remote inventory (exact account/bucket/prefix, keys, observed identities and trusted expected SHA-256/size where available); no upload, seeding, overwrite, deletion, or other provider mutation is required. Allow a previous campaign's trusted receipts or a user-reviewed external inventory as expected evidence. When a trusted source digest is absent, report completed download and computed digest, not independent integrity PASS. Round-trip includes both legs and independent end-to-end hash verification. Download retention is configurable where compatible with the declared mode; a hash-only streamed read must be labeled as such, not a saved download. No mandatory local source directory for download-only.
- Define mode-specific benchmark denominators and counters for the selected duration: upload-only counts production-confirmed uploads, download-only counts completed downloads (separately count independently hash-verified downloads), round-trip counts fully independently verified upload/download pairs. Report each metric separately, with actual operation and byte counts, verification level, active direction, concurrency, and failures; never conflate production confirmation with independent SHA-256 verification or compare unlike modes as equivalent throughput. MVF(T) denotes independently verified files in the selected T-minute window where applicable; MVF40 is the default-window metric, MVF45 is just one possible explicitly selected comparison. Time and resource budgets, authorization fences, checkpoints and Queue visibility apply to every mode. Read-only workload execution under a read-write grant must still issue zero mutations for download-only; reuse the existing read-only grant where requested, without forcing a mode switch. Downloads do not create duplicate upload History cards or masquerade as uploads. Add regression tests for all three modes, optional readback, no-write download-only and no-download upload-only, remote inventory provenance, interruption and mixed-mode accounting.

- Read-write campaigns are the normal laboratory workflow, including continuation after expiry/restart. Do not force the operator into a separate read-only session simply to resume unfinished work. Offer explicitly approved read-write continuation for the exact existing campaign/QA prefix, bound to the same authorized account, bucket, frozen manifest digest and remaining operation IDs; show its scope and remaining budgets before approval. Reconcile uncertain operations using reads within that read-write grant before deciding whether a write is necessary; never replay a confirmed mutation or blindly retry an ambiguous commit. Only demonstrably uncommitted eligible work may proceed to writes, with existing destination claims and conditional publication intact. Retain existing read-only reconcile/resume commands as backward-compatible non-mutating diagnostics, not as the required campaign workflow. Use a distinct continuation command rather than silently changing the old read-only resume command's semantics. Revocation, expiry, account changes and scope violations still fence dispatch. Add tests for renewal, continued writes, lost acknowledgements, zero duplicate commits and exact-scope isolation.
- Support at least 2,000 files immediately in one folder tree, using an inventory architecture intended to scale toward 10,000+ files, with immutable relative-path/size/SHA-256 master manifest, including duplicate contents at different paths. Distinguish single-file jobs from explicitly requested folder jobs. Internal batching is transparent and never changes the user's job semantics.
- Metric MVF(T) = independently verified file count within the configured T-minute window for modes with independent verification; also report mode-specific throughput defined above, actual elapsed time, requested duration, effective deadline, and why any window ended early. Use monotonic timing; include discovery, staging, transfers and finalization in end-to-end benchmark, and also report active transfer time. Never exceed the effective session/authorization deadline or explicit cost/byte limits. Reserve measured drain/finalization headroom; checkpoint continuously and do not admit work that cannot safely finish. Finalize durable campaign receipts by the selected window deadline or earlier when required. Support explicit authorized renewal/resume of pending work; never replay confirmed mutations or silently widen QA scope. Distinguish attempted, uploaded, verified, failed, uncertain and not attempted.
- Bounded streaming, limited queue window, no duplicate source copies, disk/RAM preflight with continuous watermarks, configurable retention (keep downloaded bytes or stream hash with receipt marking that no saved copy exists). Configurable bounded concurrency with safe default 1, measured adaptive option, backoff and real active counts. Do not claim linear scaling.
- Isolate independent per-file failures, continue others if auth/storage/global health permits, classify systemic blockers and preserve all evidence. Never convert a failed/uncertain result to PASS. No blind retries of ambiguous mutations. Crash-resume and idempotent receipt recording.
- Expand configurable size limits with resource budgeting; cover zero, chunk boundary +/-1, 1/8/10/50/100 MB and large-file streaming. 400, 1,000 and 2,000 workload profiles now; design extensible profiles for future 10,000+ workloads without requiring their live execution; deterministic synthetic repeat/rename generators with independently hashed files, no mandatory disk duplication, never overwrite user inputs. Use fixture library and local reviewed user inputs.
- Repair Cloudflare gzip/weak ETag readback: retain strict validator for existing consumers; use correct representation/identity semantics, pre/post strong metadata where available, complete decoded bytes SHA-256 and size (do not compare compressed wire Content-Length with decoded source size), reject object changes and ambiguous identity. Never strip W/ as a shortcut. Test SVG/HTML/XML/CSS/JSON, PNG/JPEG, malformed and truncated bodies, absent/weak/changed validators. Distinguish intentionally malformed source files from corrupted transfers: byte-preserving transport should pass even when preview is unsupported/invalid.

## P0: real Queue and History
- Queue retention: increase the existing normal completed-job retention default from 15 to 60 minutes, measured from terminal completion (not submission or campaign start). Existing error retention is already 60 minutes; preserve it and the existing keep-errors preference. Reuse the current configurable Queue retention controls, honor explicit user overrides, and do not introduce a second retention system. Active, pending, resumable and unresolved operations must never be discarded by terminal Queue cleanup. Expiring or manually clearing visible completed Queue entries must not delete History cards, campaign journals, receipts, or evidence required for reconciliation. Test cleanup during a 40-minute default campaign and longer configurable windows, restart, and existing preference migration. This changes Queue visibility retention, not transfer timeout, OAuth lifetime or benchmark duration.
- Every admitted file is visible in the real REDOWN Queue, with actual name, provider, progress, bytes and states, not fabricated UI entries; display pending/active/verified/failed/uncertain/cancelled and grouped folder progress. No invisibly bypassing production queue. Folder job expands into individual child rows with true progress. For thousands, virtualize or paginate, bounded memory; no dropping events. Keep ordinary queue controls working, including cancellation and provider distinctions.
- Individual uploaded files each receive their own durable History card through the normal persistence pipeline; show actual upload/verification status, provider, timestamp, filename, size, receipt and existing actions. Upload acknowledged but verification uncertain must not be presented as verified. Idempotent across restart/reconcile, immediate History refresh. Never generate extra cards just for readback.
- Explicit folder upload: carry stable parent folder-job identity through shared production dispatch and persistence; exactly one folder History card instead of thousands of standalone child cards. Show folder name/path, provider, file count, aggregate bytes, completed/failed/uncertain counts, expandable/paginated child results and receipts, per-child existing actions where appropriate. Folder card is a UX grouping, NOT an excuse to omit per-file durable evidence. Mixed results must remain visible.
- Folder preview: determine the most frequent supported image format among production-confirmed, preview-eligible folder descendants (normalize JPEG aliases; stable format tie-break lexicographically), then choose the smallest nonempty, production-confirmed, preview-decodable image of that format by original byte length; ties use normalized relative path. If the first candidate fails safe preview decoding, choose the next eligible file, then next ranked format; if none, use generic folder icon. Do not fetch or decode every child: use metadata then bounded lazy preview of candidates only. No SVG scripts, external resources, or active content. Preserve access controls, existing thumbnail cache bounds, and UI responsiveness. Internal batches do not create separate History folder cards.
