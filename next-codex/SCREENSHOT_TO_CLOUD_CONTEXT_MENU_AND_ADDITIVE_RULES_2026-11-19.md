## LATEST OWNER CLARIFICATION — same keyboard shortcut remains ADDITIVE (Nov 20, 2026)

**Supersedes earlier takeover/one-active-owner proposals.** Multiple ACTIVE screenshot shortcut cards MAY share the EXACT SAME keyboard shortcut. When it is pressed, match **ALL enabled shortcut cards with those keys** whose website conditions include the active page, and **EVERY enabled matching website-only additive screenshot rule**. Their destinations accumulate, with a single capture and one browser→Worker image upload. No shortcut takeover, deactivate-previous-card dialog, forced switch-off, implicit replacement, per-card 'winner' or restriction that only one card may be Active. There is no Exclusive Save mode or rule winner; ordinary rule Active switches are user-controlled and one rule never deactivates another.

**Duplicate default controls repeated paths:** Settings → **Single file per screenshot per directory** is **ON by default**. After collecting ALL matching rule→folder intents, compare destinations using canonical authorized provider/account/bucket/exact normalized prefix. With ON, deliver exactly **ONE image per distinct directory**, even when 10 or 100 matching rules point there. With OFF, each distinct matching rule→destination association produces its OWN physical cloud copy with a distinct object key; each shortcut rule card contributes once even if multiple OR website patterns match. Regardless of Settings: ONE capture, ONE inbound browser upload and accurately correlated per-rule and per-object receipts. Never deduplicate different authorized buckets merely because their folder display names are identical.

**Shortcut assignment UI:** Screenshot2Here can assign keys already used by another active screenshot card, **without asking to deactivate or change either card**. The saved cards are independently editable and active. When choosing an existing card to Add/Replace a folder, identify the exact card by immutable rule ID, name, website scope and current destinations (not by shortcut text alone). Only block a new shortcut that genuinely conflicts with a DIFFERENT Chrome command (e.g. Shelf History toggle) or a browser/OS-reserved key; this is NOT a screenshot-to-screenshot conflict. Dynamic Chrome shortcut registration remains subject to real manifest/Chrome command limits; don't claim new browser-wide keys are immediately usable just because locally saved.

**Default screenshot framing:** On shortcut press, capture the **whole visible area of the active browser tab** as one image (not a selected element or user-drawn crop). Explicitly distinguish this from Chrome's address bar, browser tabs, window frame, other open tabs, below-the-fold full document and other monitors. `chrome.tabs.captureVisibleTab()` captures the visible TAB viewport, **not** browser chrome UI or an arbitrarily long full webpage. If literal whole Chrome-window-frame capture is desired, it needs a separately approved/user-consented `desktopCapture` window-picker flow; never silently claim `captureVisibleTab` delivers browser controls. Keep image dimensions and capture scope truthful in receipts.

**Acceptance:** Two active cards A and B both use actual Chrome shortcut K. Both match the page, and each specifies the same folder → ONE screenshot capture, ONE browser upload and ONE cloud image in that folder (Settings ON). OFF → TWO different cloud objects. If A points to folder X and B to folder Y → one object per directory. A Google-restricted card does not contribute on YouTube; a matching All-websites card still contributes. Different matching website-only cards accumulate as well. All matching rules remain additive; only the default directory deduplication setting determines whether several rules targeting one directory create one or several files. Assigning K to B never disables A, and no takeover/deactivation prompt is displayed. Distinct unrelated Chrome commands must still be protected.

## Settings — Single file per screenshot per directory (DEFAULT ON)

**Exact user-facing setting:** Settings → Screenshot → **"Single file per screenshot per directory"**, toggle **ON by default** for new or upgraded profiles without an explicit stored value; persist OFF/ON across restart. Do not place this setting in the More → Screenshot website-to-location form, Screenshot2Here popup, or a new capture tab. Explain beside OFF: "Create one copy for each matching rule, even when several rules point to the same folder. This uses more cloud storage and Worker writes."

**ALL matching rules contribute; no most-specific-wins.** On one valid user-triggered screenshot shortcut press, match **every enabled saved shortcut card with that chord** whose website list (OR of its entries) includes the current trusted URL. Empty website list means all sites and **still matches alongside** narrower cards. Collect each destination attached to each matched shortcut card. Also collect **every enabled matching additive website → folder rule** from More → Screenshot. Each matched **rule ID + destination folder** contributes one intended delivery, regardless of overlap. A single card with two website entries that both match still contributes its destinations **once** (its website entries are alternatives, not distinct rules). Duplicate identical folders within one card's destination list are disallowed. Different shortcut chords are not triggered.

**ON / default (directory-level dedup):** Group intents by canonical authorized **provider + account + bucket + exact prefix**. Produce **exactly one screenshot file per distinct directory** for this one capture. Ten distinct matched rules pointing at one folder → **ONE object there**, not ten. Ten rules spanning three distinct folders → **ONE object in each of the three folders**. Receipt includes the identity of every contributing rule, intended deliveries, which were combined, and independently verified resulting objects.

**OFF (per-rule copies):** Do NOT collapse deliveries from **different matching rule IDs** just because they target the same directory. Fulfill **each matched rule→destination association** as a distinct Worker-side object write. Ten distinct matching rules pointing at the same folder → **TEN separate screenshot files there**. Generate collision-resistant distinct file keys (capture ID, rule ID and destination ordinal), with no overwrite. Record a rule-associated verification result for each copy. ON/OFF must not affect the site's rule matching, card persistence, shortcut assignment or screenshot capture logic.

**Transport and correctness in BOTH modes:** Exactly **ONE screenshot capture and ONE extension→existing trusted Cloudflare Worker image upload** per triggered action, regardless of matching rule count. Worker performs all server-side authorized writes; the current Worker has single-destination logic and needs a scoped extension to support these semantics. Securely authorize intended rule IDs/destinations, reuse existing File API/recorder/Raw-Secure exporter, and do not fake support for unbound buckets. Idempotency protects **retries of the SAME output intent** but must NOT collapse intentionally distinct OFF-mode rule copies. Use bounded Worker concurrency/memory, report partial failures truthfully, count matching rule IDs, unique directories, planned outputs, actual writes and verified/failed/unknown results. Do not log screenshot bytes.

**Required proof matrix:** TEN distinct enabled matching rules (e.g., multiple same-shortcut shortcut cards AND matching website-only cards) pointing to ONE directory: ON = one capture, one browser upload, **ONE R2 file**; OFF = one capture, one upload, **TEN distinct R2 objects** with separate rule-attributed receipts. Each shortcut card's matching OR website patterns count once. Two active shortcut cards with same keys are allowed and both contribute. With three distinct authorized directories, ON yields 3 files; OFF yields one object for each matching rule→folder association. Partial failures and retries preserve output intent identity.

## FOUR ARCHITECTURAL SAFEGUARDS — APPROVED NOV 20, 2026

**Binding for Codex; not yet implemented.** Keep the original additive model: multiple ACTIVE screenshot cards may subscribe to the same keyboard shortcut, and ALL matching shortcut-card destinations and matching website-only rules contribute. One user signal means ONE screenshot capture and ONE browser-to-Worker image upload. There is no Exclusive Save, priority winner or forced shortcut takeover. The global setting Single file per screenshot per directory is ON by default and applies only to THIS capture.

### 1. One central signal dispatcher
- Create ONE screenshot command-event entrypoint, not one listener/capture call per saved rule. One actual Chrome command emits one internal screenshot signal. Rule cards subscribe to signal IDs; one shortcut can have unlimited rule subscribers without adding separate browser commands for every card.
- Preserve the current src/api/shortcuts.mjs uniqueness check between DIFFERENT commands. It rejects duplicate command key bindings today. Do not mistakenly use that one-to-one bindings map as the rule-card subscription table. Put many rule IDs under one supported screenshot signal, and keep collisions with unrelated commands blocked.
- Current extension/manifest.json lacks a commands declaration. Browser-wide keys require real manifest-declared Chrome commands and genuine Chrome assignment, verified using chrome.commands.getAll(). Unlimited rule listeners do not grant unlimited arbitrary browser-global shortcuts. Do not claim keys entered into the app are registered when they are not.
- Assign a unique signalId to each intentionally distinct keypress. Coalesce retries of the SAME event only; do not use a time-based debounce that suppresses two separate rapid keypresses. Website-only rules cannot trigger captures without an eligible screenshot action.
- Browser right-click Screenshot to a specific folder remains a distinct one-off single-target action, not an implicit additive shortcut signal.

### 2. Immutable capture plan
- At trigger, snapshot the command/signal, trusted active tab ID, window ID, URL and navigation identity, all matching rule IDs and their exact authorized folder targets, the dedup setting and rule configuration version. OR website conditions within one card make that card contribute only once.
- Validate matching and folder authority before sending screenshot bytes. Freeze the planned capture and destinations: edits, disables, changes to URL scope, shortcut or dedup setting during flight may affect only a LATER capture, never this one.
- chrome.tabs.captureVisibleTab(windowId) captures the window's ACTIVE tab, not a specific tab ID. Verify the active tab/window/navigation immediately before capture and again immediately afterward. If the identity is uncertain or the user switches tabs, fail safely without uploading potentially wrong-page pixels.
- Never silently substitute a different bucket/folder for a revoked or unauthorized destination; allow separately valid planned outputs to complete with truthful PARTIAL status.

### 3. Unique capture and output IDs
- Distinguish signalId (keypress event), captureId (one image for that signal), operationId/jobId (one Worker fan-out job), ruleId (saved card identity), and outputId (one planned physical R2 object). NEW keypress means NEW captureId even when pixels are identical. RETRY means SAME captureId and SAME outputId/key.
- With directory-dedup ON: output identity is deterministically tied to captureId + canonicalDirectoryId; receipt lists ALL contributing rule IDs. With OFF: output identity is deterministically tied to captureId + ruleId + canonicalDirectoryId (and a stable ordinal only if an explicit separate intent exists). Multiple matching website conditions in ONE card count ONCE.
- Use durable output claims/journals with idempotency and retry verification so response loss, MV3 restarts, partial Worker completion or repeated requests cannot create accidental duplicate objects. Retry failed or uncertain outputs only; preserve successful ones. Do not re-capture and call it a retry.
- Report per-output attempted, verified, failed, unknown and skipped states, contributing rules and verification method; Worker acceptance (including HTTP 202) is not proof of stored R2 bytes.

### 4. Canonical directory identity
- Define one pure provider-aware destination identity helper shared by the planner and backend validation: authorized provider + immutable connection/account + bucket/container + EXACT provider-canonical directory prefix. Never deduplicate by folder display label alone.
- R2 keys/prefixes can be case-sensitive; do not blindly lowercase key paths, decode arbitrary percent escapes, normalize Unicode into different object keys, or collapse meaningful path segments. Equate only representations the provider guarantees to be the same directory. Validate root, prefix boundaries, trailing delimiter, Unicode and malformed/traversal cases.
- ON means one NEW object per unique directory PER CAPTURE, not once per directory forever. OFF means one separate NEW object per distinct matching rule-to-directory association. Same folder labels in different accounts/buckets must never collapse.

### 5. Worker and tests for the four safeguards
- Existing src/cloudflare/worker.mjs authenticates one deployment-bound account/bucket/prefix and right2cloud-module/src/cloudflare-worker.mjs has a single-target writer. Extend the EXISTING trusted Worker narrowly for screenshot-only, same-bucket multiple-prefix authorized fan-out first. Verify every target server-side. Cross-bucket/account is not operational unless separately bound, authorized and tested.
- One captured PNG can be buffered once under an explicit screenshot size budget for fan-out; do not attempt to consume a one-shot ReadableStream repeatedly or reupload once from the browser per destination. Bound CPU, Worker memory, concurrency and operation lifetime.
- Required matrix: zero matching shortcut rules => zero captures; 100 same-shortcut matching rules => one capture/upload; 10 rules to one folder => ON one object/OFF ten objects; 3 distinct folders => ON three objects; two OR website conditions inside same card => one rule claim; two real keypresses => two new captures; retry same output => no new object; mid-flight edit => unchanged plan; tab/window changes => no wrong-tab upload; same display folder name in different accounts => different identities; unauthorized output => rejected with truthful partial/failed receipt.
- Preserve current Simple/Narrow/Depth save engines and shared diagnostic recorder. Add module tests for pure matcher, directory identity, ID and planning, plus browser-level event integration and real disposable R2 proof only when available.

## FINAL OWNER DECISION — REMOVE EXCLUSIVE SAVE COMPLETELY (Nov 20, 2026)

**There is NO Exclusive Save switch, mode, designated exclusive folder, conflict resolution, automatic rule suppression, priority/winner, state stack or restoration feature in Screenshot Rules.** Remove its controls, old tests, documents and dispatch logic. Preserve only the ordinary per-card **Active ON/OFF** switch, which affects THAT rule alone, and the separate global **Single file per screenshot per directory** setting. A saved rule never automatically disables another saved rule just because their websites/shortcuts/folders intersect.

**Single deterministic additive algorithm (all entry-point types clearly separated):**
1. For a genuine, permitted **screenshot shortcut event**, resolve its keyboard shortcut and capture the foreground window/tab ID, trusted active-page URL, and immutable current rule/configuration snapshot. **If zero Active shortcut cards with that key match that URL, do not capture**; website-only rules cannot trigger a screenshot alone.
2. Match **EVERY Active shortcut card with the pressed keys**, with OR website conditions per card (empty website list = All websites); each matching card contributes **each distinct authorized destination folder in that card exactly once**. Match **EVERY Active website-only Screenshot rule** on that same trusted URL and add its one folder. Never apply specificity to exclude other matching rules. Two or more Active cards may use identical keys.
3. For a one-off **browser right-click → Screenshot → explicit destination**, treat that action as **one exact destination only**; it is NOT a shortcut event and must not inadvertently fan out through shortcut/website rules. An explicitly separate 'Use matching Screenshot Rules' context choice, if implemented, may deliberately request the additive path, but must never change the one-off meaning.
4. **Freeze the plan** before upload: the capture identity, trusted tab/window/URL, matched rule IDs, exact canonical account/bucket/prefix targets, duplicate-setting value and intended output IDs. Rule edits mid-flight affect only the next screenshot. If the tab/navigation/focus changes before capture can safely bind to the intended page, abort or explicitly fail rather than capture a different page using stale URL matchers.
5. Apply **Single file per screenshot per directory = ON by default**: group **only THIS capture's planned intents** by canonical provider/account/bucket/prefix; each distinct directory gets **ONE new screenshot object**, and its receipt lists every contributing rule. Do NOT inspect existing R2 files to decide whether this directory 'already has a screenshot' from a previous event. With setting OFF, produce one distinct object per matching **rule ID → destination** intent, with unique keys; never multiply output because two OR website conditions on ONE card match.
6. Capture the **entire visible active-tab viewport ONCE**, no user crop, then upload image bytes ONCE to the EXISTING trusted Worker (not once per rule). Worker must reauthorize all targets and perform bounded, independently verifiable writes; report confirmed/failed/unknown/partial statuses per output. A retry of the same capture/output ID must NOT create accidental extra copies; a fresh keypress creates a new capture ID.
7. Never let a rule with a missing/unauthorized folder silently fall back to a different directory. Show that intent as skipped/blocked with an accurate diagnostic, while valid independently authorized output intents may complete. Never expose screenshot bytes in logs; avoid sending captured content before scope/authorization checks.

**Removed-state migration:** If users have old draft/local `exclusiveSave`, `exclusiveDestination` or `exclusiveActivationSequence` properties, **ignore/strip these safely** without modifying their rule Active state, original destinations, website scope or shortcut keys. No stale exclusive field may change execution. Do not add a migration that deletes saved rules or disables overlapping cards.

**Acceptance:** Same shortcut across A (Google-only) and B (All websites), plus a matching website-only C: all three contributions execute on Google; only B (plus any matching website rules) executes outside Google. If all three target one exact directory, Settings ON → one object, OFF → three rule-attributed objects, ALWAYS one capture/upload. With three distinct folders, all three get one file in default mode. A second keypress, even to the same directory, creates one **new** file. Turning off A does not modify B or C. Editing a rule during upload cannot redirect that existing capture. One-off right-click Screenshot to folder X does not unexpectedly create files in B/C.
