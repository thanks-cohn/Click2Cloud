### FINAL OWNER DATA-PATH DECISION — AUTOREROUTE MUST STREAM FILE BYTES FROM THE CHROME BROWSER

**Binding clarification (Nov 20, 2026):** This is specifically for **automatic browser download rerouting**, NOT Screenshot-to-Cloud. The source bytes must be fetched/read by the **user's Chrome browser in a supported extension/browser context**, and streamed **from Chrome into the existing trusted Click2Cloud Worker**, which writes the same bytes to authorized R2. The Worker must NOT implement this feature by merely accepting a source URL and performing a separate server-side source download. The browser is the **data-plane relay**, the Worker is the trusted R2 destination/authorization gateway.

```text
Eligible website download action
  -> verify source access and exact winning download rule BEFORE interception
  -> Chrome-side authorized fetch/ReadableStream of ORIGINAL file bytes
  -> stream/pipe bounded byte chunks FROM Chrome to EXISTING Click2Cloud Worker
  -> trusted Worker validates destination, receipt identity and incoming bytes
  -> R2 verified object at selected authorized folder
  -> shared History + inspectable per-transfer receipt
```

**No local-file staging by design:** For successfully controlled/eligible transfers, do **not** intentionally start an ordinary Chrome download, write a full temporary file to local Downloads, hold the full object as a Blob/ArrayBuffer in extension memory, or require a native app. Keep bounded-memory streaming, verified bytes, source and destination identity. A source response with unknown length or an object too large for safe single-put streaming must use bounded chunk/multipart upload to the same Worker/R2 integration (each part verified; abort/cleanup on failure), rather than buffering whole file. Avoid unbounded buffering in extension/Worker/service worker. Accept real browser-side network bandwidth usage: **bytes pass THROUGH Chrome**, not a URL-only command.

**Real browser constraints:** Chrome's `downloads.onCreated`/filename suggestion do NOT expose the existing download response body; there is no general 'pipe Chrome Downloads to cloud' API. Build a controlled supported interception path that obtains an eligible URL **early enough**, then performs a consented Chrome-side `fetch` (or other documented byte-stream request) with a readable response body, and a true browser-originated streaming upload to Worker (test `ReadableStream`, `duplex:'half'` and actual Chrome extension permissions/CORS/preflight). Avoid assuming a raw `ReadableStream` transfers through `chrome.runtime.sendMessage`; streaming must remain in the one chosen browser execution context or use a separately proven bounded transport. Do not refetch the source in the Worker. Treat extensions' MV3 service-worker termination/fetch timeout as real; choose a documented, justified execution-lifecycle solution (extension page, offscreen document only for permitted documented reasons, or other verified long-running pathway), plus durable operation IDs/retry/abort; do not invent indefinite SW keepalive.

**No accidental duplicate download or missing file:** Only suppress an original local download when the browser-side interception is authorized and a viable remote stream can be established **before** Chrome commits to the ordinary download. The Chrome Downloads API may detect transfers only *after* local transfer starts; don't claim that cancellation guarantees zero local temporary bytes. If interception is unavailable or source needs inaccessible session cookies, POST body, JavaScript `blob:`, private/expired link, DRM, etc., do not silently cancel or misrepresent success: let Chrome download normally. After a remote transfer begins, cloud errors must be visible and recoverable; do not automatically trigger an unauthorized duplicate local or cloud download. Record actual local handoff status, not assumed zero bytes.

**Security/integrity:** The Chrome-side fetch must follow exact user-granted host permissions, origin/CORS semantics, cookies/credentials only when explicitly authorized; no leaking cookies, Authorization headers, signed source URLs or private URL query params to R2/Worker receipts. Worker authenticates the user/session and independently validates exact bucket/prefix, file key, upload ID, allowed stream sizes, per-part sequence and idempotency. Never let untrusted page content choose arbitrary Worker targets or fake a save receipt. Compare original browser-read size/digest (where safely obtainable) with verified Worker/R2 stored bytes; report success only after backend confirmation.

**V1 format scope remains:** Images PNG/JPG/JPEG/GIF/WebP (optional AVIF only if verified), video MP4/WebM, archives ZIP/CBZ. Files are opaque unchanged byte streams. Use the extensible file-type capability registry for later types. Do NOT expand V1 scope to audio/PDF/other formats or conflate this with Get URL's All files export filter.

**Mandatory controlled end-to-end tests:** Prove actual **Chrome HTTP response body bytes** are the bytes sent to Worker and written to disposable R2 for each V1 format. Capture evidence of browser-side byte counters, bounded heap behavior, R2 object size/integrity, chosen rule and exact folder, and no unintended local download. Run large MP4/ZIP with multipart, interrupted connection, interrupted Chrome/background lifetime, redirects, Content-Disposition, length unknown, retry/partial, 403, source unavailable, cookie-required, late intercept and two simultaneous eligible downloads. For unsupported cases verify the normal Chrome download is preserved. **If browser-originated byte streaming cannot be proven, mark automatic reroute BLOCKED, not DONE**, even if a Worker URL-fetch prototype works.

### Actual browser download-to-cloud REROUTING IS THE FEATURE — not UI-only

No extraction, transcoding, conversion or archive inspection: move the original file bytes unchanged.

Matching, UI, diagnostics, receipts and tests read the registry rather than hardcoding media special cases throughout the code. Register additional extensions/categories later without rewriting the rules page or transfer dispatcher. An unsupported type may be saved as an inactive plan only if clearly labeled **not supported for automatic routing**; do not show a live Active switch promising execution. Genuine source access, verified R2 delivery and no unintended local staging are still mandatory for supported formats. `.cbz` and `.zip` must stay distinct by filename extension even if both report `application/zip`.
