# NEXT CODEX — Agent-ready, scriptable-by-design API + release version 0.3.20

**Owner direction:** November 19, 2026. **Status:** Binding cross-cutting requirement for the current next-Codex implementation request; **not** permission to implement a computer-control agent or change system-wide privileges now.

## Product vision: future optional agents, not a new agent feature today

Click2Cloud should be engineered so that **one day, only if the owner chooses**, an authorized software agent could orchestrate *the user's own computer and connected cloud resources* through well-designed, machine-invocable APIs. The same interfaces should let developers run **repeatable, automated, large-volume function tests** without manually clicking the Shelf. Design today's API so that future authorized agent tools can reuse it instead of rewriting the product.

- **API-driven wherever feasible without needless complexity:** stable, versioned, documented API operations for the actual useful work: connection/capability inspection, authenticated accounts and buckets, directory/file listing, metadata and tag read/write, Get URL domain mapping and URL exports, original/tags/all-metadata downloads, recursive directory export, export job status, cancellation, shortcut-eligible command discovery, verified results and receipt data *generated inside the downloaded archive*. Reuse the **existing V3+1.1 `toolRegistry` and File API** and the existing trusted gateway. No independent `agentAPI`, execution engine, new Worker topology, speculative public HTTP endpoint, external agent server, or entirely new permission model.
- **Same logic for humans, scripts and future agents:** let UI menus/buttons invoke underlying canonical operations where useful. Do not force scripts to drive DOM clicks to discover file operations or parse presentation-only text. Return typed, structured results and honest states/errors, with stable object identity, account/bucket/key, scope, pagination, completion vs partial vs unknown, and actual supporting evidence. Keep presentation-only controls (focus Search, theme/toolbar layout, opening/closing cards) as lightweight local UI actions when an API wrapper would add complexity.
- **Discoverability and composition:** stable command IDs and schemas, capabilities/introspection, actionable error codes, input validation, enumerated modes, status/permission requirements and pagination/cursors. Favor commands composable as a straightforward script (list → select → act → inspect result) rather than one-off UI branches. Support optional bounded progress/cancel/status on legitimately long operations. Do not invent “verified” proof without a real observed check.
- **Automation safety without user friction:** preserve the existing trusted caller, OAuth/grants and account/bucket scope. Never provide arbitrary desktop access or credential extraction, bypass permissions, silently publish buckets, or create extra approval dialogs for existing approved operations. Future agent/computer-control integration is **opt-in future scope only**; today's task merely creates clean callable contracts. Separate read-only introspection/test operations from actual mutations, and preserve explicit user intent for public exposure and destructive effects.
- **Testability:** build or extend a **lightweight scripted API harness** using existing test infrastructure and realistic fixtures/disposable local providers, so developers can exercise most newly implemented functions repeatedly: single/many file/directory operations, tag lifecycle, multi-URL grouping round-trips, original/tags/metadata downloads, partial/incomplete receipts, status/cancel/retry, error codes, command bindings, and immutable History. Include deterministic IDs or seeded fixtures where reasonable, idempotency and eventual completion handling, no opaque UI-only success condition. Long stress loops should be *possible by running the harness again*; **do not add a never-ending self-running loop or unbounded production cloud activity**. Report exactly which functions are tested through the API and which are UI-only.
- **Preserve the explicit product boundaries:** bulk ZIP receipt `RRReceipt-<time-stamp>-<job-number>.json` exists **ONLY INSIDE THE DOWNLOADED ZIP**. Debug More → Downloads shows lightweight expandable job cards but no receipt copies. Ordinary History stays EXACTLY AS IS for existing right-click saves; no new bulk download rows or History schema changes. The daily count belongs on the existing **Chrome extension action icon**, not on the Shelf. No broad Worker architecture redesign, no extra user authorizations/confirmation popups, and no blanket responsive/theme/accessibility test matrix.
