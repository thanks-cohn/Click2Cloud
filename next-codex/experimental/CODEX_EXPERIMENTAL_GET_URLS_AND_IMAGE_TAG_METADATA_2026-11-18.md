# NEXT CODEX / EXPERIMENTAL — Right-click Get / Add URLs + durable image tags

**Date:** November 18, 2026  
**Status:** NEW EXPERIMENTAL IMPLEMENTATION FEATURE, **not currently shipped**.  
**Repository:** Click2Cloud only; isolated feature branch.  
**Priority:** After the immediate Search/gallery/Manager UX and existing API/shortcut fixes have their own validation gates. Experiment behind a user-visible feature flag, off by default, with no surprise public exposure or mutation of private buckets. **No general Worker architecture redesign, pair-Worker migration, or cross-account copy/move redesign is in scope.** Use only the existing trusted provider/file paths and changes strictly necessary for these specific features.

## Cross-cutting implementation rule — API-first only where practical

This entire experimental set should **extend the existing versioned Click2Cloud V3+1.1 API and existing File API where sensible**: file/directory selection, Get URL, multi-domain mappings, metadata tags, download modes, bulk exports, menu preference descriptors and machine-readable outputs. Define stable input/output contracts for useful scriptable operations, with the existing authorization and provider adapters. **Do not** create a competing API, Worker execution engine, new History subsystem, or artificial wrappers for local presentation/DOM actions. Prefer the simplest implementation that fully delivers the requested behavior; avoid extra architecture, repeated confirmations and speculative future features. **History must stay exactly as it is today**, reserved for the existing right-click save workflow. Bulk-export receipts exist ONLY within downloaded ZIP archives.

## 1. Preserve the previously agreed Get URL workflow

The earlier product plan was **Cloudflare R2 object → right-click Get URL**, not "download a URL into R2". A user with an authorized public custom domain mapped to a bucket should be able to produce/copy a real URL for a selected object and then bulk export actual URLs from a directory.

- In Explorer, **right-click a file/image → Get URL / Add URLs** (label distinction can be polished). Show an object-scoped editor with a list of **multiple user-authorized website/custom-domain URL mappings per object**, not a single URL field.
- **THE SAME FIRST-TIME GATE FOR FILES AND DIRECTORIES:** If the selected file, directory prefix or its parent R2 bucket has **no usable, verified public URL/domain mapping**, Get URL must first display the exact question **`Allow Public URL?`** with **Yes** and **No** choices. **No** closes/returns with no changes and all content private. **Yes** starts the existing Cloudflare domain-association/public-URL setup workflow and shows the domain input; do **not** immediately open public access merely from pressing Yes. The setup flow then validates the associated bucket/domain and creates the applicable file URL(s) or directory export mappings when configured and saved. This is the SAME flow regardless of whether a user first right-clicks a file or directory; don't add separate, inconsistent onboarding. Do not invent working URLs or alter bucket/domain settings silently. A proposed URL stays unverified until validated.
- Support **adding/editing/removing URL entries** in the object's metadata/manifest, with website/domain identity, canonical object key, URL, source (`verified custom domain` vs `user-provided reference URL` if provided), validation/provenance, last-verified time and optional human label. Keep multiple website URLs attached to one object and preserve their distinctions. Distinguish an arbitrary user-pasted URL from a verified public URL.
- A URL derived from a verified mapping must encode all object key components correctly without inventing prefixes or public domain policy, including special characters, spaces and Unicode. Avoid leaking private objects/tokens or granting public access automatically.
- **Right-click a directory → Export URLs**: enumerate the exact authorized scope, group by file/object and output **each URL on its own line** under its file identity, with an optional machine-readable CSV/JSON/JSONL export preserving all URLs per file. Directory-wide exports must use bounded, paginated listing and honor incomplete scopes; no falsely complete bulk exports, no provider calls on every copy when durable inventory is fresh and valid.
- Keep copy-to-clipboard for one verified URL or multiple URLs, with a clear indication of what was copied. If there are no verified URLs, don't pretend the object has a live public link.

This is a fundamental Click2Cloud product pillar with an experimental first implementation, not a replacement for existing right-click save-to-cloud.

## 2. Right-click image → Add/Edit Tags stored as metadata

- Right-click a saved image in File Explorer or from preview → **Tags / Edit Tags**. Enter multiple plain-text labels; add, remove and edit. Show saved tags in image Properties/preview and make them accessible programmatically through the **canonical File API** (not a GUI-only note).
- Treat this as persistent **cloud object metadata**, not only IndexedDB/Chrome local storage. Codex must determine the safe, documented R2 metadata mechanism. If R2 requires replacing/copying an object to change user metadata, handle it through the existing trusted File API with exact-object identity, verified effects, permissions, conflict checks, quotas and explicit consent where needed; a durable versioned sidecar may be safer than rewriting multi-GB images, but must be justified and kept object-consistent. Never assert an R2 metadata update is a cheap in-place edit without confirming the provider capabilities.
- Don't alter the original image pixels, EXIF, filenames or actual file bytes. Preserve existing Content-Type, custom metadata, HTTP headers, ETag/version assumptions, public URL mappings, permissions and source data; detect lost-update races, moved/deleted objects, rename/copy behavior and account transitions.
- Tags need a documented schema with bounded length/count, Unicode normalization and case-insensitive search semantics (if future tag search is planned). Unknown or unsupported tags must not be silently discarded. Use an object-identity/generation or ETag-conditioned update/reconciliation mechanism; clearly distinguish pending, verified, failed and uncertain updates.
- Allow safe single-object tag editing first. Bulk tagging, folder inheritance, automated categorization, embedded EXIF tagging and full-text tag search are explicitly **not** part of this initial experiment unless separately authorized.

## 2A. Exact owner-specified Add Tags pop-up and metadata capacity meter (November 19)

- Right-click **an image** → **Add Tags** opens an object-scoped pop-up with a text input, existing tag pills below it, **Save** at the bottom and **X** at top right. Prefill from the persisted JSON tag array in that exact object's R2 custom metadata. New input is **comma-separated**; typing `funny, tag1, tag-2, tag3` and pressing **Enter** converts those entries into separately removable pills. Pressing Enter stages tags **locally**; only clicking Save authorizes a durable metadata update. Reopening must display the saved pills, and removing a pill followed by Save persists its removal. Scroll the pill section vertically when many tags accumulate without letting the dialog grow offscreen. Never auto-save on Enter or X.
- Maintain a meaningful **live character counter AND live byte budget with an ALWAYS-RESERVED 100-BYTE SAFETY BUFFER**. Treat R2's nominal 8,192-byte total custom-metadata limit as **8,092 usable bytes**, never advertise the last 100 bytes as available. For example: `36 characters in pending tags · 412 / 8,092 usable metadata bytes · 7,680 estimated remaining (100 bytes reserved)`. If actual estimated usage is `used`, display remaining as **`max(0, 8,192 - used - 100)`** and accept new metadata writes only if total measured/estimated custom metadata usage **including all existing fields** is `<= 8,092` bytes. Show `100 bytes reserved for safety` near the counter. Do not subtract 100 twice or make the visible limit inconsistent with Save validation. The user specifically requests this conservative allowance to prevent provider limit errors. A character cap alone is insufficient: emoji, non-ASCII Unicode, JSON quotes/escaping, existing metadata entries and metadata key names consume different amounts of bytes. Recalculate with actual serialized JSON and UTF-8 (e.g. TextEncoder); include **all existing custom metadata**, not just the tag array. Read existing object metadata via a read-only R2 HEAD / metadata query when opening, and reload/revalidate it on Save. Cloudflare does **not** expose a literal `metadataBytesRemaining` response field; app computes an **estimate** from returned `customMetadata`. Provider write confirmation is authoritative.
- Limit submitted metadata **by byte budget**, not an arbitrary number of pills or raw character count. R2 currently sets a **total 8,192-byte custom metadata limit per object**, but our enforced and user-visible budget is **8,092 bytes** because **100 bytes are permanently reserved as a fixed safety margin**. Account for all existing metadata and metadata key/value serialization/encoding. Validate empirically against R2; where accounting is uncertain, err on the side of rejecting the new write rather than relying on the reserved bytes. When the pending update would exceed the safe cap, show `Too much metadata` with count and remaining budget; disable Save without discarding the draft. Do not truncate tags or overwrite unrelated metadata. If a later sidecar strategy is approved, it must be a separate explicit migration and still be durable and race-safe; do **not** silently switch storage.
- Preserve existing user metadata, content headers, object identity, ETag/version and original bytes; if a concurrent edit changes the object/metadata before Save, return a clear conflict and offer refresh without overwriting it. Do not claim R2 can edit custom metadata in-place; verify supported safe write/copy/sidecar mechanism before release.
- Use the same current-object identity and display semantics in the app API, and test Unicode/emoji byte accounting, JSON escaping, fixed 100-byte deduction (including exact 8,092-byte boundary, 8,093-byte rejection, no double-subtraction, and existing metadata), preexisting metadata near limit, add/remove/reopen, many scrollable pills, concurrent editors, rewrite failure and provider `MetadataTooLarge`.

## 2B. Exact owner-specified Get URL pop-up and directory export interaction

- Right-click **file** → **Get URL**. **If no valid public URL exists for this file/bucket, show `Allow Public URL?` Yes / No BEFORE the URL editor**, identically to directories. On Yes, show the Cloudflare-linked domain setup/input workflow; on No, leave private and exit. Once a usable mapping exists, the popup has a **domain input at top**, current verified public URL(s) below it, and **Save** at bottom and **X** upper right. In the setup view, invite: **"Connected Domain with Cloudflare? Add it to give this bucket URLs!"**. Input domain → Enter stages candidate URL(s) for that file; repeat to add further URLs, each visibly shown below, without replacing previous entries. Save persists authorized mappings. Next time Get URL opens, the input remains at top and saved, independently validated URLs appear beneath. The user can remove stale/incorrect entries. Never label a hypothetical URL verified.
- **A registered domain is not automatically connected to the target R2 bucket.** Validate the Cloudflare bucket/custom-domain association and path/prefix transformation before creating live public URLs. The first-time **`Allow Public URL?` Yes / No** is the explicit user choice to BEGIN setup, not permission for an invisible immediate bucket-wide public-access mutation. Domain configuration/Save must be deliberate and clear about real exposure scope (Cloudflare custom-domain association can expose other objects in a bucket, not merely the selected file/prefix); show that essential scope note in the same workflow rather than adding repetitive dialogs. A generic input must not silently deploy DNS or open public access. Cloudflare's current **100 custom domains per bucket** limit applies to verified bucket domain mappings; the UI must show real provider limits and not promise unlimited verified domains. An indefinite list of proposed local strings is not the same as an indefinitely long list of actual public URLs.
- Right-click **directory** → **Get URL**. Directories are key prefixes and do **not** have a personal/public object URL by default. **If no usable public URL mapping exists for that directory prefix/bucket, the FIRST view must ask exactly `Allow Public URL?` Yes / No (same wording and sequence as for a file).** Yes begins the Cloudflare-linked domain workflow and reveals its input; No exits and keeps the content private. Do not show a fabricated personal URL for the directory. On subsequent invocation (or whenever a usable mapping already exists), ask **"Get all URLs from directory?" Yes / No**. If Yes, enumerate only **eligible file types** within the exact directory scope with correct pagination/completeness evidence and apply existing authorized domain mappings.
- Provide checkboxes **CSV**, **TXT**, **JSON**, independently selectable (one or all). A visible **Export** button downloads the selected formats, each as a genuinely machine-readable file with file path/key, URL(s), verified status, provider/bucket identity as authorized, and completeness/provenance; TXT emits a clear grouped, parseable layout. Mark incomplete scans; never export a partial scan as complete. X cancels without changes.
- **MANDATORY: ONE FILE CAN HAVE MANY URLS; GROUP ALL OF THEM UNDER THAT SAME FILE IDENTITY IN EVERY EXPORT.** Never flatten URLs into an anonymous list, treat each URL as a separate file, or accidentally merge two files with the same filename in different directories. Use stable, unambiguous `objectId` (provider + account/bucket + full exact object key, or an equivalent canonical non-secret identity) and preserve `bucket`, `key`, `relativePath`, `urlCount`, domain/site labels, URL verification status/provenance and URL order. The export must make the **one-to-many object → URLs** relationship directly parseable and visually recognizable, even with spaces, Unicode, duplicate filenames, multiple domains and filenames containing commas.
  - **JSON:** `files` array has exactly one entry per source file; each entry contains `objectId`, `key`, `relativePath`, `urlCount` and `urls: [{url, domain, status, provenance}, ...]`. Do not turn URLs into separate unrelated JSON file records. Include schema version, export scope and completeness.
  - **CSV:** use **one row per URL**, repeat the *same* `objectId`, `bucket`, `key`, `relativePath`, `urlCount` across all rows for that file, and include `urlIndex`, `url`, `domain`, `status` (and safe provenance). A parser groups rows by `objectId`, sorts by `urlIndex` and reconstructs all URLs belonging to that single source file. Use valid CSV quoting/escaping; preserve zero-URL files with an explicit row or a documented separate summary and never count rows as distinct source files.
  - **TXT:** render a clearly delimited **FILE** section with full object key/path and `urlCount` followed by one URL per line, then a separator and the next FILE section. Provide deterministic escaping/delimiters for filenames/newlines and enough structure to parse without guessing which URL belongs to which file. Mark zero-URL files and unverified URLs accurately.
  - **Receipts:** report separate counts for source files, URL entries and files with multiple URLs; preserve per-file URL groupings in the export receipt, not just a grand total. Test 0, 1, 3, 100 URLs attached to one file; 2 files with identical basenames but different paths; 10,000 files, CSV and JSON round trips, domains, escaping and partial enumeration. No silent URL deduplication across distinct domains or deletion of legitimate entries.
- User-entered additions staged by Enter become durable only with Save; preserve verified mappings and exclude private objects from invented/public exposure. The existing File API and object metadata ownership remain authoritative; no second URL store or UI-only fake receipts.


## 2C. THREE distinct image download choices (owner request, November 19)

These are exactly three visible right-click image actions, not two; implement within the existing File API, without another public API:

1. **Download** — download the original stored image, byte-for-byte unchanged. R2 custom object metadata does not automatically become embedded image metadata.
2. **Download with Tags** — create a portable download containing the saved Click2Cloud tag list embedded in the image in a supported native metadata format (such as XMP, where technically valid). Preserve pixels and existing embedded metadata; verify the tags can actually be read back. For a format where safe embedding is unsupported, explicitly offer the user an alternative original image plus a companion tags JSON file rather than silently claiming tags are embedded. Never alter the original cloud object.
3. **Download with All Metadata** — export a portable ZIP containing the unchanged original image and a machine-readable JSON manifest containing all available safe, user-exportable object metadata: R2 custom metadata (including saved tags), HTTP metadata, key/bucket/provider, size/MIME type/ETag and available version and timestamps, verified domain/public URL mappings if separately maintained, provenance, schema version, plus a missing-or-redacted-fields list. Original embedded EXIF/XMP already remains in the original bytes. Exclude OAuth tokens, signed grants, signing keys, authorization headers, credentials and private diagnostics from the manifest even under the label "All Metadata". Do not invent unavailable information.

**Cloudflare implementation reality:** The Worker/R2 API can return the image bytes, the separate customMetadata map and httpMetadata. It does NOT natively implement these three download variants or automatically embed object metadata into an image's EXIF/XMP. Implement transformation/encoding as explicit product behavior using validated libraries and streaming/bounded formats; do not buffer arbitrary huge objects in a Worker. Keep consistent object-version/ETag read, exact file bytes in original/all-metadata choices, verified tag extraction in the tag-embedded choice and accurate receipts. Reject uncertain results, preserve user consent and never rewrite the source object for a download variant.

**UI/acceptance:** Show **Download**, **Download with Tags**, **Download with All Metadata** as three discoverable choices on image right-click; current Download behavior must stay intact. Test image formats separately (JPEG, PNG, WebP, unsupported formats), Unicode/JSON escaping, embedded metadata preservation, missing Cloudflare customMetadata, large streamed files, stale/concurrent tag changes, privacy, manifest schema, ZIP integrity, re-import and download failure. The two new options are experimental/feature-flagged OFF until proven; never imply they already ship.


## 2D. Bulk directory Download with Tags / Download with All Metadata and opt-in right-click visibility (November 19)

**Owner UX:** In File Explorer, BOTH an individual file and a DIRECTORY may be right-clicked to request either new download mode. **These are two new optional right-click entries, not a mandatory nested Download submenu.** Keep the existing plain Download directly accessible at all times.

### THREE independent Settings checkboxes — in ordinary Settings (Debug OFF)

- `Show Download with Tags in right-click menu` — when OFF, hide this extra right-click action for files and directories; when ON, show **Download with Tags**.
- `Show Download with Metadata in right-click menu` — when OFF, hide this extra right-click action for files and directories; when ON, show **Download with All Metadata** (same action, explicit user-facing name).
- `Nest under Download` — when OFF (DEFAULT), show the enabled options as direct siblings of **Download**. When ON, replace those direct entries with one **Download >** submenu containing **Download original**, plus only the two enabled modes. Never create a submenu with no added modes. Preserve the original direct Download behavior when both new mode checkboxes are OFF.

The two Show flags must **default OFF until their feature is implemented and validated**, and the Nest flag defaults OFF. After validation/opt-in, showing new actions is immediate and direct, not automatically nested. These settings are separate from the Keyboard Shortcuts editor and cannot create a separate API/dispatcher. Persist preferences, migrate safely across upgrades, respect all three themes/light/dark, redraw already-open context menus safely, and retain the user's exact options across restart. Generate both file and directory context menus from the **same canonical File API action descriptors**, with different validated input scopes. Do not confuse Chrome native web-page right-click menus with the File Explorer object/directory context menu.

### Directory Download with Tags

- Right-click folder/prefix -> **Download with Tags** -> traverse the entire authorized directory subtree, preserving relative paths inside a single ZIP. A directory is a logical prefix, not an R2 folder body. Do not rely on only currently loaded UI rows.
- Include all downloadable ordinary files; for tagged supported images, export the image with actual verifiable embedded tags without changing R2 original bytes. For unsupported image formats, retain the original file plus a companion `.tags.json` (and an explicit explanation in the export manifest). For ordinary non-image files, retain the original bytes and represent any supported object tags as companion metadata where embedding is not supported. Never omit a file solely because its type cannot hold embedded tags.
- Provide a machine-readable archive manifest with per-object key, relative path, expected/verified size, tag export status (embedded/companion/none/failed), errors and total scope completeness. If any file can't be exported, present an honest partial-result receipt and unambiguous manifest; never mark ZIP as complete.

### Directory Download with All Metadata

- Right-click folder/prefix -> **Download with All Metadata** -> stream a ZIP that preserves the original bytes and relative structure for every authorized file.
- Alongside each object put a safe versioned `.metadata.json` manifest entry (or a collision-safe metadata subtree) with available provider metadata, full permitted user-defined metadata including tags, HTTP headers, object identity and timestamp, verified URL mappings if available, completeness/provenance, and explicit absent/redacted fields. Include a top-level `manifest.json` with schema, export time, source bucket/prefix, counts, summary hashes/checksums when verified, per-file states and a machine-readable errors list. Never let metadata sidecar filenames overwrite user files that happen to be named `.metadata.json`; use a reserved/collision-proof archive path strategy.
- **All Metadata does not include private credentials**, OAuth tokens, Worker secrets, signed grants, raw diagnostics or unverified public URL claims.

### Safety, scale and end-to-end gates

- Use R2 prefix + continuation cursor listing, explicitly choose recursive vs immediate-children behavior (**default recursive for folder download**) and preserve complete authorization scope. Fetch object metadata separately where listings omit fields; recheck each exact-object ETag/version before packaging. Detect renamed/deleted/changed objects mid-export instead of mixing unrelated versions.
- Use streaming ZIP creation with backpressure and bounded memory; support ZIP64 or clearly reject archives that exceed the chosen library/container limits. Cloudflare Workers have a **128 MiB per-isolate memory limit** and HTTP streaming connections may be interrupted; never buffer the whole directory in the Worker or browser. For huge or long-running jobs, propose a separately approved durable checkpoint + temporary artifact executor, rather than claim browser-independent archive delivery exists already. Do not create private cloud staging artifacts or recurring charges silently.
- The user can choose Cancel; show actual progress (items scanned, bytes packaged, files omitted/failed), output mode and estimated cost where reasonable. After a disconnect, never claim a finished download or an intact ZIP. Never delete any source objects. Avoid duplicate object bytes in the archive for retries. Validate safe relative paths, zip-slip prevention, Unicode, filename collisions and traversal loops.
- Test 0/1/100/10,000 entries, nested prefixes, inconsistent metadata, 8,092-byte application tag budget, Unicode, unsupported formats, large objects, pagination, interrupted streams, expired grants, empty folders, denied scope, partial failures, multiple open Shelves, all combinations of the THREE Settings flags, and exact direct-vs-nested menu state.
- **Feature flags OFF until verified; no live R2 production mutation or deployment authorized.** A successfully completed streamed archive is distinct from an accepted/queued export. Keep honest status in the active API/download result and in the embedded ZIP receipt; **do not store bulk-export events in History**.

## 2E. REQUIRED DEFAULT BULK DOWNLOAD RECEIPTS — "WE GOT THE RECEIPTS" (November 19)

**Non-negotiable product behavior:** **EVERY completed bulk directory download includes an accurate, machine-inspectable reconciliation receipt INSIDE THE DOWNLOADED ZIP ONLY, by DEFAULT, named EXACTLY `redown-remote-receipt.json`.** This applies to plain **Download**, **Download with Tags** and **Download with All Metadata** when applied to a directory. No extra receipt checkbox, no Debug Mode dependency, no separate receipt file/download, no receipt pop-up, **NO HISTORY RECORD AND NO HISTORY CHANGES**. The receipt belongs to the archive bytes, not to Click2Cloud's right-click-save History/Save Results. Preserve ordinary individual-file Download behavior and avoid UI friction. A URL-list export (CSV/TXT/JSON) must retain accurate source/grouping and completeness information in its chosen exported format, not create a separate receipt-history entry.

### Source inventory → exported archive → delivered result: one-to-one reconciliation

- **BEFORE:** Snapshot the complete authorized R2 source directory/prefix with paginated listings, stable snapshot/cursor provenance, timestamps, and exact inventory completeness. Per object: original key/path, bucket/account identity as safely displayable, size, MIME type (if known), available ETag/version/checksum, last-modified and metadata/tags presence. Distinguish source facts from unobserved or changed objects. A prefix is not a single stored directory object.
- **AFTER:** Map every source item to an exact relative ZIP path (or explicit omission) with mode: original unchanged; embedded tags; companion tags JSON; original + metadata JSON; failure/skip; unexpected/extraneous ZIP entries. Include output filename, actual bytes streamed/packaged, available computed cryptographic SHA-256 for transferred bytes, metadata manifest identity, and whether readback/embedded-tag verification was performed. **Do not call an R2 ETag a SHA-256 or a verified byte checksum unless proven so.**
- **RECONCILIATION:** Every source inventory entry gets a disposition: exported and verified at the available boundary, skipped with reason, failed, changed during transfer, cancelled or unknown. Detect missing/duplicate entries, duplicate output paths, filename collisions, incomplete pagination, size/hash mismatches and additional unexpected entries. Include expected/observed file and byte totals, tagged-object counts, errors, timestamps, exact operation/export ID, explicit source/ZIP mapping and provider evidence. Never quietly report success when scope or delivery was partial.
- **DELIVERY EVIDENCE:** Distinguish clearly between `SOURCE_LISTED`, `SOURCE_READ`, `ZIP_ENTRY_WRITTEN`, `ARCHIVE_FINALIZED`, `BROWSER_DOWNLOAD_REPORTED_COMPLETE`, `CLIENT_BYTES_VERIFIED` (only if actually checked), and `ON_DISK_CONTENT_VERIFIED` (only with legitimate actual readback). Browser streaming or a successful HTTP response **does not prove what the user has on their filesystem**. If Chrome download completion is observable, record it; otherwise mark local delivery as unconfirmed. No fabricated before/after disk snapshot.
- **RECEIPT EXISTS ONLY INSIDE THE DOWNLOAD:** Place exactly one versioned **`redown-remote-receipt.json`** in every *successfully finalized bulk ZIP*, using a collision-safe reserved archive path while preserving that exact filename. No alternate `click2cloud-receipt.json`, no additional `.txt`/HTML receipt, no separate standalone receipt download, **no History/Save Results insertion, no extra permanent receipt ledger**. The JSON contains exact source-to-archive mapping, statuses and verifiable evidence. If an archive fails or is interrupted before finalization, report failure in the active download interaction; **do not emit or persist a separate receipt** or fabricate a ZIP with a completed receipt. The receipt is an archive-content artifact, and its recorded delivery state must not assert later browser/on-disk confirmation that cannot be known at ZIP-finalization time.
- **HUMAN + MACHINE:** The JSON receipt inside the ZIP answers "Which R2 folder was selected? Which source files were found? Which archive paths were written? What was omitted or changed, with what evidence?" Use plain-English fields/summaries and stable machine-readable JSON with schema version, counts, file mapping, available validated hashes and statuses. Report `ARCHIVE_FINALIZED` only when observed; never claim subsequent browser completion or on-disk verification from an embedded receipt created earlier. No separate CSV/TXT receipt products. Exclude credentials, signed grants and secrets.
- **API-FIRST AND HISTORY IMMUTABLE:** Use the existing canonical V3+1.1 API / File API for normal file selection, inventory, metadata reads and bulk export where practical. Generate the receipt **as part of the ZIP stream only**; no new receipt authority, History record, Save Results item or lasting per-export receipt copy. **Do not touch History implementation, schema, retention, filters or behavior**: it remains exclusively for existing right-click save activity. The **Chrome extension icon badge** may use existing History for its already-supported remote saves and, if local-download counts are needed, a small separately maintained numeric completion total that does not create or persist any export receipts or mutate History. Count actual confirmed delivered files, never ZIP sidecars/receipt as additional files.

### Acceptance gates

Test full/partial/empty directories, thousands of objects, nested prefixes, duplicate names, invalid paths, metadata/tag transformations, mixed provider/object change mid-read, cancelled or interrupted streams, restored sessions, multi-Shelf views, receipt-export privacy, a ZIP that never finalized, an archive that finalized but never reached Chrome's completed-download state, complete browser downloads, and exact inventory/ZIP per-object reconciliation. Require automated validation that a claimed complete export has one output for each intended source file and **a receipt present by default**. Demonstrate both pleasant one-click user behavior and programmatic auditability. These requirements DO NOT authorize the removed Worker architecture overhaul, existing transfer routing changes, new authorization popups, or production cloud deployment.

## 3. API, reliability, privacy and test requirements

- Define shared File API operations, e.g. `listObjectLinks`, `addObjectUrl`, `removeObjectUrl`, `readObjectTags`, `setObjectTags`, `exportDirectoryUrls`, but reuse actual app naming/authorization contracts. Same exact source/account/bucket/key identity as File Explorer; idempotency keys, verifiable receipts, explicit metadata ownership and tested fallback for failures.
- Preserve all existing metadata and previous URL/tag values under interruptions and concurrent edits; do not rewrite the whole object unsafely just to attach a label.
- Never turn private content public as a side effect of a Get URL click. Explicit authorization is required for domain configuration, user metadata writes and any cloud-chargeable mutation.
- Test identical `Allow Public URL?` Yes/No first-time UI on a file, directory and missing bucket-domain mapping; No causes zero mutations, Yes only opens setup until saved, existing verified mappings skip the gate, and exposure scope is explained without a second surprise prompt. Also test 0/1/many URLs on one image, two linked custom domains, unavailable domain, missing custom domain, public vs user-supplied unverified references, URL encoding, private object access, one/multiple tags, add/remove, Unicode, rename/move, large objects, stale accounts, multi-Shelf concurrent edits and failure/restart recovery. Verify directory export for 100/10,000 objects and incompletely loaded lists.
- Use mocks/disposable test objects only; **no automatic production R2 mutations, domain changes or public exposure**. Report actual Cloudflare docs and any remaining provider capability gates.
- Maintain separation between source-derived cached filename metadata, true R2 object metadata/sidecar, public-domain mapping, and ordinary verified save receipts. None is a stand-in for the other.
