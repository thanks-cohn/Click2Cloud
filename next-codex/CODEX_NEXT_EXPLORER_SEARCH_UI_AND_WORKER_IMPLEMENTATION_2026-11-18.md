## STEP 2 — EXPERIMENTAL: right-click multiple URLs and image tags metadata

Follow [experimental Get/Add URL mappings and image tags task](experimental/CODEX_EXPERIMENTAL_GET_URLS_AND_IMAGE_TAG_METADATA_2026-11-18.md). User wants real right-click image **Get URL/Add URLs** capabilities with multiple Cloudflare-linked website URLs per object and per-directory exports (one URL per line grouped by file), plus **right-click image → add/edit tags** saved as persistent cloud metadata, not just browser-local notes. This is a Click2Cloud product pillar, but initial implementation lives under `next-codex/experimental` and **must be feature-flagged OFF by default** until validated.

**Identical public-URL first-run gate for FILES and DIRECTORIES:** If there is no usable verified public URL/domain mapping for the selected file or directory/bucket, right-click **Get URL** must first ask exactly **`Allow Public URL?` Yes / No**. **No** exits with no changes; **Yes** begins the Cloudflare-linked domain setup/input workflow, without immediately publishing anything. Once configured and validated, continue with normal file URLs or directory URL exports. Warn within the same workflow when bucket-level domain exposure affects more than the selected object; no redundant prompts. See experimental section 2B.

No auto-enabling public access. Respect R2 custom-domain authorization, multi-site URL identity, metadata overwrite/sidecar constraints, object version/ETag concurrency, verified receipts and record persistence across restarts/renames. Do not assume metadata editing is an in-place cheap operation. Prototype the canonical API and UI only if safe; otherwise preserve as gated proof with explicit blocker.

**Directory Get URL exports MUST preserve one-to-many file→URLs groupings:** if a file has multiple verified website URLs, JSON keeps one file record with `urls[]`; CSV repeats the same exact object identity in one row per URL with a URL index; TXT groups URLs beneath a clearly identified file heading. Preserve exact bucket/key/relative path identity, verification/provenance and separate file-vs-URL counts, including in the export receipt. Do not flatten into anonymous URL lists or treat URLs as distinct files. See experimental section 2B.

**Three image download modes:** Add distinct options **Download** (original, unchanged), **Download with Tags** (embedded tags where format supports verified embedding, otherwise explicit companion JSON alternative), and **Download with All Metadata** (ZIP containing unchanged original plus all safe exportable R2 metadata in JSON). See the full experimental specification, section 2C. Do not pretend R2 natively embeds customMetadata into image bytes, and do not leak credentials.

**Directory bulk downloads and controlled menu layout:** Right-click on a directory may produce a streamed recursive ZIP in **Download with Tags** or **Download with All Metadata** mode, preserving all files and an auditable, machine-readable manifest. Two ordinary Settings checkboxes independently show/hide each new direct menu option. Third checkbox **Nest under Download** (DEFAULT OFF) changes only presentation to a submenu. The two optional actions are OFF by default until implemented/verified; once enabled, they are immediate direct actions, NOT nested, unless the user checks Nest. Preserve unchanged Download, no extra public API, no unbounded Worker buffering, and no claim that unconfirmed ZIP streaming succeeded. See [exact mode and menu specification](experimental/CODEX_EXPERIMENTAL_GET_URLS_AND_IMAGE_TAG_METADATA_2026-11-18.md#2d-bulk-directory-download-with-tags--download-with-all-metadata-and-opt-in-right-click-visibility-november-19).

**Default receipts on ALL bulk directory downloads — mandatory product feature:** Plain directory Download, Download with Tags, and Download with All Metadata each automatically include the exemplary **`RRReceipt-<time-stamp>-<job-number>.json` INSIDE THE DOWNLOADED ZIP ONLY**, reconciling R2 source inventory against actual archive entries. **NO bulk-download records, receipts, or status entries in ordinary History/Save Results: History stays EXACTLY AS IT IS for existing right-click saving.** No standalone receipt download, no extra UI prompt, no separate receipt ledger. Never claim browser download/on-disk verification from an archive-embedded receipt. See [experimental specification, section 2E](experimental/CODEX_EXPERIMENTAL_GET_URLS_AND_IMAGE_TAG_METADATA_2026-11-18.md#2e-required-default-bulk-download-receipts--we-got-the-receipts-november-19). **Do not reintroduce the removed Worker architecture redesign.**

**Debug-only Downloads cards:** Add [More → Downloads](../Issues_and_Bugs/Issues/P1_DEBUG_DOWNLOADS_MORE_SECTION_2026-11-19.md) visible **only while Debug ON**, showing **one individually expandable card per major download**. The collapsed card visibly shows the directory name, job timestamp, download mode, count/size and status; expanding shows additional safe job information, progress/errors, and the associated receipt filename (NOT receipt contents). The full receipt remains **inside the ZIP only** with unique filename **`RRReceipt-<time-stamp>-<job-number>.json`**, using a UTC millisecond timestamp and distinct stable job number/ID. **Nothing from bulk exports goes into History/Save Results.** This UI is a lightweight diagnostic view over existing status signals, not a second receipt ledger, new API or Worker architecture overhaul.
