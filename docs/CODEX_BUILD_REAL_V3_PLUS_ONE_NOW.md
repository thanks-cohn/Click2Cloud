## P0 CORRECTION — COMPLETE INSPECTABILITY, NO DIAGNOSTIC SHORTCUTS (OWNER REQUIREMENT)

**This section takes precedence over any earlier wording about “minimal traversal,” “fewer files inspected,” “earliest suspicious boundary,” “sparsity,” “lightest API,” or “fewer agent iterations.”** Those phrases describe benefits of a *fully instrumented, readily inspectable system*; they are **NOT** implementation targets that permit dropping checks, excluding paths, hiding inconvenient failures, suppressing signals, narrowing tests, or prematurely declaring a diagnosis.

**The actual objective:** Build a **comprehensive, programmatically inspectable and traceable surface covering the entire V3+1 right-click engine and the external boundaries it uses**, so any authorized human, ChatGPT Work conversation, or Codex agent can obtain faithful evidence quickly and correlate it with the exact menu, operation, module, source revision and failure. **Completeness, correctness, and detecting real errors are mandatory. Low overhead is a hard constraint on *how evidence is captured*, never justification for reducing coverage.** Less investigation work and fewer repair iterations are downstream *outcomes*, not success proxies that an agent may game.

### Anti-Goodhart, fail-visible rules

1. **Never optimize the metric by eliminating the work being measured.** An agent must not reduce “files inspected,” “diagnostic queries,” “iteration count,” or “latency” by skipping mandatory observations/tests, shortening the supported failure catalog, ignoring a provider/mode, or declining to investigate an unresolved discrepancy. No reward or acceptance credit for fewer steps unless failure-detection completeness, accuracy and regression invariants are at least as strong as the full-coverage baseline.
2. **No silent blind spots.** Enumerate and instrument all supported critical operations, state transitions, input/output/error branches, external handoffs, and lifecycle recoveries in a source-backed coverage map. The map must include Simple, Nested/Narrow, Depth, activation, authorization, inventory, MenuSpec, every nested native row/action, Chrome registrar ACKs, capture, all provider dispatch paths, actual upload/readback receipts, History/counters, persistence, concurrency and MV3 restarts. Add a boundary to the catalog whenever new code/capabilities are added. Coverage must be traceable to implementation and tests; one green boundary does not certify its hidden internals.
3. **Signal *every critical decision*, not every line.** Strategic checkpoints must be sufficient to distinguish all supported failure categories and transitions. If a single signal cannot distinguish two materially different failures, split or enrich that checkpoint. “Cheap” means compact and efficient, **not sparse to the point of ambiguity**.
4. **Never infer success from absent evidence.** Missing, dropped, evicted, stale, out-of-order, mis-correlated or uninstrumented signals are explicit `UNKNOWN / COVERAGE_GAP / OBSERVATION_DROPPED`, never `HEALTHY`. The API must expose these with the responsible boundary and recommended focused probe. A visible green checkpoint asserts only its specific verified condition.
5. **No early-stop investigation on a plausible origin.** An initial suspect may prioritize the *next inspection*, but the system must check the dependency chain and relevant sibling/independent branches needed to establish the conclusion. A failing prerequisite may coexist with an independent hidden defect. Report evidence-backed candidates, unknowns and alternative causes instead of prematurely declaring root cause.
6. **No manufactured simplicity.** Never disable instrumentation to make benchmarks pass, silently lower fixture coverage, artificially shrink menu trees, truncate results without paging/completeness flags, omit error branches, mock away native Chrome or provider boundaries, or redefine “PASS” around easy cases. If performance and coverage conflict, redesign the capture mechanism and report measured tradeoffs; do not silently sacrifice either.
7. **Diagnostic query is read-only, but exhaustive within declared scope.** The agent must be able to inspect a complete paginated logical menu tree, its omitted candidates and versioned generations, select any row at any depth, and request the full available path of correlated boundary evidence. Any unavailable native/browser/provider evidence must be explicitly marked unverified—not invented, omitted or converted into a green check.
8. **Guard against agent self-deception.** Require adversarial fault injection: hidden error behind a green parent signal, missing beacon, two unrelated simultaneous faults, stale ACK with correct-looking MenuSpec, one provider failing while others work, partial Depth inventory, false provider success, and cross-mode regression. These must expose errors/gaps. Agent reports must include failed or unresolved tests, not just passing subsets.

### Required proof of *complete* debugging coverage

- Produce a **source-backed observability inventory** mapping each supported engine operation, public interaction, material branch, state transition and error class to its checkpoint(s), data fields, reason codes, source anchor, unit/integration/live verification and owner. For each feature, show **covered / partially covered / unobservable / not tested** and why. “90%” is a metaphor about helpful signal coverage, **not a coverage ceiling**.
- Require **fault-injection coverage over the entire catalog**, including negative/error branches, intentionally silenced/misleading checkpoint scenarios and independent cascading faults. Maintain a failing test when a supported boundary lacks a signal, correlation or accurate UNKNOWN report.
- Prove that diagnostic **queries** correctly retrieve/interpret the available evidence: nested menu rows at all supported depths, diffs across all modes/providers, operation-level breadcrumbs before/after failures, stale/dropped-event metadata, and artifacts across MV3 restart. Partial pagination must have truthful completeness and continuation.
- Preserve all normal business verification: checks for actual provider receipts, Chrome ACK, actual browser parity, auth and mode isolation are **not substitutes** for Glaciaring signals, nor vice versa.
- **Measure latency without weakening instrumentation.** Run matched on/off benchmarks against a fixed comprehensive coverage manifest and identical fault-injection corpus. If diagnostics exceed an overhead budget, optimize storage, encode/event layout, sampling of *redundant high-volume details* only (never mandatory branch outcomes), lazy query rendering or deferred work. Report all remaining gaps and limitations.
- Only **after coverage/detection/accuracy gates pass**, measure whether an agent can understand and fix issues with less manual code traversal, screenshots, repetitive prompts and Codex runs. **These efficiency measurements can never be used to justify dropping diagnostic coverage** or terminating diagnosis early.

**Acceptance priority:** `observability completeness + detection accuracy + truthful gaps + unchanged business behavior + user privacy` **first**, `low measured runtime overhead` **as a simultaneous hard constraint**, `faster agent investigation` **as a consequence**. A system that is fast by failing to detect errors is a **FAIL**, even if it requires fewer Codex runs.

### Goal: faster correct diagnosis, not more debug data

The non-negotiable success criterion is **faithful inspectability and full coverage of supported critical engine behavior** with near-negligible measured latency overhead. Once detection accuracy and completeness are proven, easier Work/Codex investigation and fewer repair iterations should follow. Never turn reduced agent activity into an excuse to skip signals or checks. The owner's illustrative “90% map coverage” means coverage of important behavior/interactions, **not a target for logging 90% of lines**.

A failed right-click should let a diagnostic agent immediately distinguish, using only cheap signals and previously observed evidence: `auth → R2/bucket activation → Worker readiness → inventory → Simple/Nested/Depth projection → MenuSpec → native registration → action resolution → source capture → upload → provider readback → History/counter`. It should expose the **complete available correlated boundary trail** and identify **evidence-backed candidate origins**, with direct navigation to owning source/tests but without skipping checks or assuming an early candidate explains everything. Subsequent blocked steps are cascade symptoms, not automatically independent root causes. Missing signals remain `UNKNOWN`; green checkpoints indicate only that their narrow assertion passed.

### Runtime non-negotiables

- **Complete critical-boundary coverage with compact signals:** Optional injected diagnostic sink; each significant operation/decision/transition/failure branch emits enough typed enum/code + attempt/epoch/generation/revision information to distinguish its supported states. No raw request/response bodies, stack capture, per-click deep cloning/JSON, source URLs, tokens, object names, or network reporting on the hot path. Use bounded fixed-size buffers and record dropped/evicted data.
- **Three tiers:** cheap passive observations only if benchmarks allow; explicit authorized **Debug Mode** for detailed inspection and console/export; **deferred** compact causal analysis and redacted receipt on definitive failure or terminal uncertainty.
- **No ordinary debug spam:** Do not render diagnostic codes/console messages/panels during normal use. Keep essential *user-facing* save error status independently visible; never hide actual failures merely because Debug Mode is off.
- **No behavioral dependency:** Disabled, missing or throwing diagnostics must never change the result of authorization, menu application, source capture, saving, receipt verification, or REDOWN History. Fail-open **observations**, fail-closed security/receipt checks.
- **No second engine:** Instrument the existing single authorized registrar, activation owner, file API, provider dispatcher and verified completion handoff. Do not duplicate Cloudflare Worker provisioning, provider OAuth, saved-file database, history/counters or the full Explorer.
- **Lazy root-cause narrowing:** Inspect only the failed operation's dependency neighborhood first; follow explicit `requires / produces / retry-of` relations, never temporal proximity alone; distinguish missing observations, independent faults, possible origins, and downstream blocked work. No unbounded replay/probing of cloud services.
- **Future-proof modules:** Adding an S3 adapter or replacing Depth should only register a small stable boundary/capability manifest. Never modify Simple, Nested, or the diagnostics core to add a provider.

### Menu twin, exact logical pairing and regression baselines

- Compile **one** deterministic immutable, credential-free MenuSpec first, with complete bounded tree, ordering, action vs item identity, labels, nesting, separators, reasons, omission index, authorization scope and revision; every visual mirror/agent inspector/native Chrome plan consumes this **same** structure.
- Implement read-only inspection, structured desired/generated/acknowledged/observed menu diffs and pure **simulation** with **zero** capture/cloud write/History/success effects. Native click, human mirror and agent simulation must resolve the **same canonical action** at the same acknowledged generation and eligible context. Any live agent action requires separately granted execution authority.
- Preserve REDOWN's existing serialized native registrar and callback semantics where practical. A Chrome ACK is **not** independently observed native pixels; true menu parity needs installed Chrome evidence. Never claim perfect visual sameness without it.
- Establish versioned **known-good mode/provider baselines** and immutable golden scenarios. When Nested changes, test that Simple and Depth output/config, all independent provider leaves and verified destinations remain intact. If a regression occurs, report precisely which actions/items changed and the smallest owner; do not rewrite unrelated modules.
- Build an **inspectable logical mirror** so the owner can express the desired result by editing/viewing the tree rather than repeatedly explaining each nested interaction. Converge by focused code or config changes and tests, **not autonomous production source rewrites**.

### Agent consumption without expensive or unsafe infrastructure

Design **how Codex/ChatGPT Work actually obtains the diagnostic evidence from a different machine or sandbox**, not just how an extension-local function returns it. Provide a stable, bounded, sanitized, machine-readable **user-authorized export** (e.g., portable Agent Debug Receipt, MenuSpec snapshot, generation diff and test fixture ID) that can be attached or passed to a coding agent without exposing private routes or credentials. Evaluate an ephemeral, explicitly approved read-only diagnostic bridge only if it demonstrably reduces manual iteration; no default public server, no background uploads, no persistent external telemetry, and no new production dependency on ChatGPT connectivity.

A debug receipt must carry enough source revision/build/stage manifest and **focused reproduction instructions** that a fresh Codex/Work conversation can immediately pick the responsible subsystem without repeatedly requesting logs or screenshots. The agent access path must respect allowlisted senders, explicit consent, redaction, bounded payloads and the distinction between diagnostic read/simulation and privileged live actions. Benchmark export cost outside the hot path.
