# Boot/login source repair

Base main: `0222969`. Branch: `dev/p0-remotes-boot-login`, version 0.3.13. Latest owner contract overrides older automatic next-login initialization rules; it does not remove saved setup approval or explicit setup APIs.

## Reproduced first boundary

The browser harness imports actual baseline background/app modules with real IndexedDB and dependency-fixture Chrome APIs. A single synchronous IndexedDB-open exception is injected after nonempty configuration is persisted. Baseline CURRENT caches that rejected `opening` promise; background `dataReady` and `ready` also retain their rejected startup promise. Subsequent getConfiguration, loginStatus and loginBegin all return ENGINE_STARTUP_FAILED with startup cause STORAGE_UNAVAILABLE, even though the one-shot fault has ended. This reproduces a specific source failure chain consistent with the reported symptom. It is not a capture of the owner's Windows exception; that precise original exception remains unavailable.

A second actual DOM reproduction identifies the inert controls: the global `[data-view]` tab binding also matched `#shell[data-view=remotes]`. Clicking its Cloudflare status descendant immediately invoked the container tab handler and replaced Remotes. The repaired binding selects only `header nav [data-view]`; the production runtime asserts the container has no tab handler.

Other verified code causes: auth/describe requests read CURRENT unconditionally; login waits for native reconciliation; successful OAuth and loginBegin both initialize Cloudflare automatically; app bootstrap waits for unrelated reads and replaces Remotes with Startup unavailable/Retry on any error. Historical hash/attention events can then reopen another view. The existing connection element can be detached by Cloudflare status while later connection code queries it by document ID, causing a null-element error and apparently inert controls.

## Single-owner corrections

- The API declares authentication, capabilities, attention inspection and engine health independent of saved configuration. Initial authorization, closed schema, auth confirmation and response-authorization remain intact. State-dependent requests still use the same CurrentStore validation plus Chrome's prior-native/missing-CURRENT guard. No fake/default configuration is supplied on failure.
- Existing loginBegin/loginStatus own all authentication. Optional `loginBegin({verifyOnly:true})` rechecks identity through existing OAuth authority/status without launching a second OAuth flow or calling R2. Normal login finishes with authentication status, never initialization. onConnected only notifies observers; notification failure cannot undo verified auth.
- Trusted Chrome credential storage remains mandatory. Its initialization coalesces concurrent calls but clears a rejected attempt. CURRENT open likewise clears synchronous rejected attempts; a closed cached database clears on InvalidStateError without replaying writes. Fresh requests can recover; genuine missing/corrupt records stay blocked.
- Per-operation API read errors expose bounded safe code/stage/causeName. getEngineHealth completes its read-only inspection and reports storage blocked separately from native/backup state. Native coverage objects no longer accidentally turn a successful health inspection into a partial API envelope.
- Background imports do not reconcile native menus. Native maintenance belongs to actual extension/browser lifecycle events, explicit configuration/setup actions or native save dispatch. Local `.ready` validates local state only and is retryable; no rejected native promise owns login. All accepted engine messages still use the same trusted sender/schema/response handler.
- Remotes is static initial HTML and immediate production rendering. Optional configuration/session/capability reads run independently, with one quiet retry for defined transient read failures and read-only boot timeouts. No top-level awaited boot blocks installing event listeners. Every document opens Remotes; Chrome 141+ onOpened events also reset a retained document only in its own window (ordinary focus/OAuth return does not reset it); old hashes/attention do not open dialogs or select another tab. User-selected tabs survive late reads/notifications.
- Remotes retains the existing connection element and login handlers; detached elements update safely. Synchronous and asynchronous button failures receive contextual feedback. Configuration failure appears in a small Remotes card with explicit safe diagnostics; Log in, Save results, Cloudflare status, Manager and tabs remain actionable or explain their own limitation. Settings/cloud status results reject stale tab intent. No startup apology or Retry ritual.

## Preservation and proof boundaries

CURRENT/IDB, encrypted recovery, OAuth grants/client/extension identity, existing setup ledger, Worker implementation/protocol, destinations and native menu compiler are preserved. No cloud resources are created/modified during this task. Existing domain setup/repair tests explicitly invoke setup instead of expecting login to perform it. The new runtime tests assert zero non-auth Cloudflare requests, resource writes and implicit menu registrations through login, plus exact configuration/approval equality.

The production-runtime harness uses real Chromium, production background + Shelf + OAuth code, real browser IndexedDB, simulated Chrome APIs and synthetic provider replies. Reloads, full browser process restart, worker-module reimports, slow/failed native registration, transient storage, corruption, missing records, offline identity and cancelled sign-in are covered. These are not actual installed Windows Chrome, real MV3 suspension or live OAuth consent. Genuine unpacked-extension/Windows/live checks are recorded independently in the handoff.
