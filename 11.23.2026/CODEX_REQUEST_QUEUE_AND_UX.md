## 2A — AGENT-NATIVE ENGINEERING AND AUTOMATED OPERABILITY (IN SCOPE, RELIABILITY FIRST)

**Design goal:** Within this Queue/History V2 and approved UX work order, make behavior **programmatically operable, observable, and verifiable**. A user click and an authorized automation should exercise **the same underlying production application operation**. This is an architectural/testability requirement, **not a request for an extension-wide refactor, new product feature, HTTP server, or parallel implementation**. Apply only where safe and where it improves stability or demonstrable test coverage.

### A. Shared production contracts — one implementation
- Identify the existing provider, Queue, History, navigation, settings, and preview contracts. For new/refactored **in-scope** logic, put validation and state transitions in small reusable functions/services with explicit inputs/outputs and versioned record contracts. Keep UI event handlers thin: input → call the same internal operation → render returned state.
- Allow automated tests to invoke those same underlying operations directly through authorized internal modules/test adapters. Do **not** duplicate provider saving, OAuth, History accounting, retention, export, or navigation rules in a test-only engine.
- Prefer internal typed functions, message contracts, state machines, and dependency injection over an HTTP API. **Do not introduce new network listeners, privileged web-page endpoints, browser permissions, or third-party dependencies solely for agents.**
- Preserve existing Chrome permission boundaries; privileged actions remain accessible only through their already-authorized extension contexts and checks. Never expose OAuth tokens, private URLs, account secrets, raw diagnostic payloads, or arbitrary provider mutations through an agent interface.
- Keep test hooks/fixtures in the test harness, behind test-only dependency injection/build boundaries. No unprotected production debug switch, hidden writable API, or privileged command channel.

### B. Script the REAL UI wherever feasible
- Create/extend an automated Chrome extension harness (use existing project tooling when available) that loads the actual built extension and exercises **real UI interactions**: click, keyboard, focus, scrolling, expansion, theme and navigation changes, Settings persistence, Queue filters, typed page jumps, Full/Compact cards, preview/lightbox, and exports.
- Assert **visible UI state and persisted application state**, not merely that a mocked callback returned success. Test `⋯` More with Debug Mode ON/OFF: Downloads never appears; test narrow windows and all supported themes, including Remote V1's preserved cards.
- Include real browser lifecycle cases: reload, closing/reopening Shelf, multiple extension windows, IDB upgrade blockage, service-worker sleep/restart, storage limits, and interrupted export. Use controllable disposable Chrome profiles; do not mutate the owner's live browser data.
- For native Chrome context menus, browser gesture restrictions, OAuth consent, and external provider behavior, distinguish **automated installed-Chrome verification**, **simulated API tests**, and **owner-assisted/manual live acceptance**. A synthetic `chrome.contextMenus` event is not proof that Chrome's real context menu appears. If automated native interaction is unavailable, report that exact gap rather than fake passing results.

### C. Reproducible machine-controlled scenarios
- Provide deterministic, seeded fixtures to exercise **100,000 metadata History records (benchmark only)**, many queued/active/waiting jobs, screenshot and standard saves, calendar boundaries, page 1/middle/last/direct jumps, visibility filters, retention settings, and repeated concurrent receipts.
- Simulate years of chronological data, malformed/legacy metadata, repeated IDs, out-of-order statuses, simultaneous writes, unavailable preview URLs, account disconnections, rate limits, 401/403, service-worker interruptions, disk/IDB quota exhaustion, and an interrupted/partially completed History export.
- Build failure injection at **observable boundaries** (before/after durable receipt, during IDB transaction, at restart/reconciliation, during export), rather than modifying production upload code to force results. Prefer the existing fixture and recorder infrastructure.
- Prove bounded memory through paged/cursor access and lazy previews. Test large *stored* datasets without hydrating or rendering all records or actually starting 100,000 cloud uploads. For extreme job counts, stress the projection/scheduler **synthetically**; preserve each provider's actual concurrency limits.
- Make simulated clocks and provider responses deterministic. Preserve realistic production semantics: synthetic fixtures never imply actual cloud verification.

### D. Structured evidence and automated assertions
- Expose safe, read-only inspection of relevant **in-scope** state through existing trusted extension diagnostics/test contracts: operation ID, provider, state, terminal time, History record ID, reconciliation status, page/cursor count, export receipt, and sanitized error code. Keep ordinary UI accessible without requiring diagnostic mode.
- Every test should assert **invariants**, not only screenshots: one destination-specific attempt → one History card; replay does not duplicate; successful jobs clear only after durable accounting/recovery checkpoint; errors remain inspectable; old History remains intact; previews never block saving; retention/record cap affect only intended layers; dates and pages are complete and stable.
- Output machine-readable test reports (e.g. JSON) and a human-readable summary containing commit/build, Chrome version/environment, fixture seed, exact commands/exit codes, assertions, observed outcomes, performance/memory measures, and redacted artifacts. Record failures and `UNVERIFIED`/`BLOCKED` conditions explicitly.
- Separate the **fast per-change suite** from the **100k benchmark, browser stress, and genuine cloud tests**; provide reproducible commands for each. Do not run the most expensive stress campaigns on every tiny UX edit.

### E. Safety and implementation boundaries
- **Reliability outranks testability.** Do not alter a stable save path solely to make it easier for an agent to script. When a seam would risk existing behavior, wrap the current contract from the outside or record the unsupported automation step.
- All automated external provider actions must use explicitly authorized test accounts/destinations. No unapproved real uploads, credential changes, deletion, bucket creation, OAuth scope changes, or deployments. Do not let simulated retries generate real remote writes.
- No agent harness code may become a prerequisite for running the shipped extension. If the harness fails, the application must still operate normally.
- Scope stays limited to **Queue/History V2 and the listed UX**. Do not turn this into a general automation framework for Files, Remotes, provider engines, Screenshot Manifests, future History transplant, or unrelated services.
- Deliver an **automation coverage matrix** identifying what is unit-scriptable, browser-automated, real-provider verified, owner-assisted, or impossible to automate with current tooling—and why. **Never equate simulation with actual Chrome/provider acceptance.**

**Acceptance principle:** A coding agent should be able to reproduce most Queue/History/approved UX behavior, inspect sanitized evidence, compare it to executable rules, and identify regressions **through the same production logic a human uses**—without making the product less secure, stable, maintainable, or simple.
