# ReDown Cloud Usage Continuity — implementation request

## Objective
Prevent a routine browser-extension uninstall/reinstall from granting another free allowance when the same cloud account is reconnected. Preserve direct-to-cloud transfers and avoid a dedicated server or mandatory ReDown account. Scope this branch exclusively to allowance persistence and required integration/tests; no unrelated UI, provider, or transfer refactors.

The example allowance is 30 free saves and $12/year unlimited. Preserve existing allowance-period semantics and license configuration if already defined; do not silently change pricing, daily/lifetime policy, or grant a separate full allowance per destination. Clarify any policy conflict in handoff. Serverless storage is user-controlled and is a deterrent, not tamper-proof enforcement.

## Design
- Inspect existing quota/licensing, provider authentication, storage adapters, operation receipts, and test harness before editing. Use one shared continuity engine, not independently implemented quota policies.
- Google Drive: investigate documented appDataFolder storage with the same app identity and least necessary permissions. OneDrive: investigate documented approot app folder access. Dropbox: use an explicitly identified ReDown metadata location within existing authorized access, without switching full-drive saves to restricted app-folder access. R2 and S3: use a clearly named dedicated ReDown metadata object in authorized storage; distinguish account and bucket scope and disclose any limitations.
- Verify current official provider APIs and required scopes. Do not silently expand permissions, impersonate provider system files, scatter hidden markers, scan arbitrary files, or recreate records after user requests deletion. Disclose purpose and location, honor removal and disconnect controls. Keep metadata out of normal transfer listings where the official app-specific storage mechanism allows. Never store credentials, filenames, URLs or file contents in usage metadata.
- Maintain a local cache and recover authoritative available records from connected cloud accounts before issuing a new free allowance. Reconcile only compatible identities and periods, preserve counts across reinstall, browser restart, update and reconnection, and avoid multiplying the free quota across providers. Document that a fully fresh install connecting only a new account cannot recover unseen records. Desktop companion may be supported only if already present and authorized; no new required desktop installation.
- Use a versioned minimal schema, stable scoped account identifiers, idempotent operation IDs, and provider-supported conditional writes/conflict handling. Define how concurrent operations reserve and finalize free usage without double-counting retries or verified failures. If a provider cannot safely support atomic updates, document and test the limitation rather than claiming strict global enforcement. Distinguish confirmed missing metadata from timeout, authentication failure, malformed data and permission denial; never treat transient errors as a fresh allowance. Make unavailable states actionable without endless retries. Keep existing paid-user transfers independent of free allowance recovery where appropriate.
- No claims of cryptographic tamper resistance for client-held secrets or user-writable records. Preserve the existing paid license validation mechanism; do not introduce new payment infrastructure.

## P0 — User-controlled save destination (mandatory)
- For Google Drive, OneDrive and Dropbox, provide a persistent per-connected-account preference with two explicit modes: **ReDown folder (DEFAULT)** (ordinary default saves in a visible folder named exactly `redown` under the authorized drive root) and **My Drive** (use the existing direct-to-drive saving behavior exactly as implemented before this branch, including its existing destination resolution; do not force root if the existing mode resolves elsewhere). Apply the equivalent root/prefix choice to R2 and S3 only if supported by existing destination semantics. Initialize the preference to ReDown folder for accounts without an explicit saved preference, including existing accounts on first use of the new setting; preserve any explicit preference thereafter. Expose the choice in the existing destination/settings interface without an unrelated redesign.
- The choice must be real routing behavior, not cosmetic: apply it consistently to default saves, supported upload flows, and screenshots while preserving explicitly selected destinations, rules and existing folder hierarchy. An explicit save-here target takes precedence over the default. Create the ReDown folder only when necessary, reuse it reliably, avoid duplicate folders, and never silently redirect a failed save to a different location.
- User file destinations and continuity metadata are independent. Google Drive appDataFolder and OneDrive approot are for application metadata, not a substitute for the visible ReDown folder; Dropbox must retain authorized full-drive functionality. Changing save mode, renaming or removing the visible save folder, or switching default destination must not by itself reset the allowance. Keep any required metadata separate, clearly identified and disclosed; do not use hidden or misleading filenames.
- Test that ReDown folder is the default for accounts without an explicit preference, that selecting My Drive reproduces the pre-change saving behavior, both modes for each applicable provider, explicit-folder overrides, setting persistence across reload/reconnect and reinstall where authorized backup is available, folder creation/reuse, permissions and errors, and identical quota accounting in both modes. Include destination IDs/paths in test receipts (redact private information); never include user filenames or paths in continuity metadata. Treat failure of either destination mode or quota continuity across mode switches as a release blocker.

## Verification and handoff
Provide repeatable scripts/fixtures and machine-readable receipts for first use, 29/30 and 30/30 boundaries, complete uninstall/reinstall with same account, reconnect and update, different account limitations, concurrent clients and retries, interrupted writes, conflicts, missing/corrupt records, auth failures, user removal, offline recovery, provider switching and paid-user regressions. Test provider adapters with mocks and separately document real-provider tests requiring credentials; never use or commit secrets. Existing transfer/authentication regressions must be checked. Distinguish verified, mocked, and untested behavior. Report changed files, commands, evidence, limitations and follow-up items. Keep the implementation confined to this branch.
