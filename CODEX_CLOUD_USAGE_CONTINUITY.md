# ReDown Cloud Usage Continuity — implementation request

## Objective
Prevent a routine browser-extension uninstall/reinstall from granting another free allowance when the same cloud account is reconnected. Preserve direct-to-cloud transfers and avoid a dedicated server or mandatory ReDown account. Scope this branch to allowance persistence, user-controlled save destinations, automatic local Laboratory receipt preservation/interruption recovery, transient transfer failure recovery, and their required integration/tests; no unrelated UI, provider, or transfer refactors.

The example allowance is 30 free saves and $12/year unlimited. Preserve existing allowance-period semantics and license configuration if already defined; do not silently change pricing, daily/lifetime policy, or grant a separate full allowance per destination. Clarify any policy conflict in handoff. Serverless storage is user-controlled and is a deterrent, not tamper-proof enforcement.

## Design
- Inspect existing quota/licensing, provider authentication, storage adapters, operation receipts, and test harness before editing. Use one shared continuity engine, not independently implemented quota policies.
- Google Drive: investigate documented appDataFolder storage with the same app identity and least necessary permissions. OneDrive: investigate documented approot app folder access. Dropbox: use an explicitly identified ReDown metadata location within existing authorized access, without switching full-drive saves to restricted app-folder access. R2 and S3: use a clearly named dedicated ReDown metadata object in authorized storage; distinguish account and bucket scope and disclose any limitations.
- Verify current official provider APIs and required scopes. Do not silently expand permissions, impersonate provider system files, scatter hidden markers, scan arbitrary files, or recreate records after user requests deletion. Disclose purpose and location, honor removal and disconnect controls. Keep metadata out of normal transfer listings where the official app-specific storage mechanism allows. Never store credentials, filenames, URLs or file contents in usage metadata.
- Maintain a local cache and recover authoritative available records from connected cloud accounts before issuing a new free allowance. Reconcile only compatible identities and periods, preserve counts across reinstall, browser restart, update and reconnection, and avoid multiplying the free quota across providers. Document that a fully fresh install connecting only a new account cannot recover unseen records. Desktop companion may be supported only if already present and authorized; no new required desktop installation.
- Use a versioned minimal schema, stable scoped account identifiers, idempotent operation IDs, and provider-supported conditional writes/conflict handling. Define how concurrent operations reserve and finalize free usage without double-counting retries or verified failures. If a provider cannot safely support atomic updates, document and test the limitation rather than claiming strict global enforcement. Distinguish confirmed missing metadata from timeout, authentication failure, malformed data and permission denial; never treat transient errors as a fresh allowance. Make unavailable states actionable without endless retries. Keep existing paid-user transfers independent of free allowance recovery where appropriate.
- No claims of cryptographic tamper resistance for client-held secrets or user-writable records. Preserve the existing paid license validation mechanism; do not introduce new payment infrastructure.

## P0 — User-controlled save destination (mandatory)
- For Google Drive, OneDrive and Dropbox, provide a persistent per-connected-account preference with two explicit modes: **ReDown folder (DEFAULT)** (ordinary default saves in a visible folder named exactly `redown` under the authorized drive root) and **My Drive** (use the existing direct-to-drive saving behavior exactly as implemented before this branch, including its existing destination resolution; do not force root if the existing mode resolves elsewhere). Apply the equivalent root/prefix choice to R2 and S3 only if supported by existing destination semantics. Initialize the preference to ReDown folder for accounts without an explicit saved preference, including existing accounts on first use of the new setting; preserve any explicit preference thereafter. Expose the choice in the existing destination/settings interface without an unrelated redesign.
- The choice must be real routing behavior, not cosmetic: apply it consistently to default saves, supported upload flows, and screenshots while preserving explicitly selected destinations, rules and existing folder hierarchy. An explicit save-here target takes precedence over the default. Create the ReDown folder only when necessary, reuse it reliably, avoid duplicate folders, and never silently redirect a failed save to a different location.
- User file destinations and continuity metadata are independent. Google Drive appDataFolder and OneDrive approot are for application metadata, not a substitute for the visible ReDown folder; Dropbox must retain authorized full-drive functionality. Changing save mode, renaming or removing the visible save folder, or switching default destination must not by itself reset the allowance. Keep any required metadata separate, clearly identified and disclosed; do not use hidden or misleading filenames.
- Test that ReDown folder is the default for accounts without an explicit preference, that selecting My Drive reproduces the pre-change saving behavior, both modes for each applicable provider, explicit-folder overrides, setting persistence across reload/reconnect and reinstall where authorized backup is available, folder creation/reuse, permissions and errors, and identical quota accounting in both modes. Include destination IDs/paths in test receipts (redact private information); never include user filenames or paths in continuity metadata. Treat failure of either destination mode or quota continuity across mode switches as a release blocker.

## P0 — Automatic local JSON receipts and interruption recovery (mandatory)
- The Python Laboratory must automatically save a machine-readable receipt of all work completed so far, without requiring the operator to click Download, remain logged in, or retain an active cloud authorization. Save directly to the existing authorized local campaign receipt directory, print its absolute path and proof filenames when possible, and provide a human-readable SUMMARY.txt. Retain existing receipt schemas/filenames where compatible. Do not require a cloud write or Chrome download to preserve local evidence. Do not silently store personal data outside the authorized receipt location.
- Persist durable operation intent before dispatch, verified outcomes and checkpoints incrementally throughout the run. Use atomic snapshot replacement and durable journal writes; do not depend solely on end-of-run callbacks. Finalize a complete or partial JSON receipt on normal completion, deadline, authorization expiration, logout/revocation, explicit cancellation, connection failure, native disconnect, or other handled error. On abrupt Chrome/CLI/process termination or power loss, reconstruct from the last durable journal on next startup, marking unresolved outcomes uncertain; do not promise a final write after the process or disk becomes unavailable. Surface disk-full/write errors explicitly and preserve the last valid evidence.
- Receipts must include campaign/window identifiers, frozen manifest identity, timestamps, termination reason, elapsed time, planned/confirmed/failed/pending/uncertain counts, bytes, throughput, last durable checkpoint, audit state and evidence paths, and an exact continuation command when applicable. Preserve prior windows/receipts; do not claim independent content or location verification that was not performed. Do not include tokens, pairing codes, or credentials. Keep these receipts independent of free-allowance metadata.
- Authorization expiry or logout must halt newly unauthorized remote operations, not local evidence collection. Resume only with an explicitly authorized fresh grant and the same frozen campaign scope; reconcile uncertain publications using existing production evidence before any retry, never replay confirmed writes, and do not silently create a fresh campaign. Preserve receipt access while logged out, including local/offline checking. Never extend or bypass grants to finalize receipts.
- Regression fixtures: normal completion; expiry mid-transfer and during audit; logout/revocation; network/native disconnect; cancellation; deadline; browser and CLI crashes followed by restart; disk exhaustion and interrupted snapshot writes; resume after partial completion and lost acknowledgement. Require accurate counts, readable receipts, explicit uncertainty, no new unauthorized writes and no duplicate publication. Verify the receipt path is available without another cloud login.
- Reference the newer Laboratory implementation and handoff at commit `1bad4007678fd3f2dcb628a3681598850feeb36e` on `codex/redown-11-26-2026-fixture-library-mvf45` (ReDown 0.3.32.4, `11.26.2026/fixture-library/HANDOFF.md`). Inspect the branch's actual Laboratory baseline before implementing; reuse existing journal/checkpoint/recovery machinery rather than duplicating it. If that newer code is absent, report the dependency and identify the minimal compatible integration required; do not silently merge unrelated work or modify the separate fixture-library branch. Distinguish verified behavior from outstanding integration or live Windows tests.

## P0 — Automatic transient transfer failure recovery (mandatory)
- Motivation: the Windows owner campaign at ReDown 0.3.32.4 completed 554 of 555 production-confirmed uploads, with 554 independent location matches, zero staging bytes, and one failed operation. The reported journal diagnosis was an isolated HTTP 502 with no automatic retry; verify the error classification and reproduction against source/available redacted evidence. Do not treat the original campaign as a full pass or assume the provider failure is preventable.
- Recover automatically from eligible transient failures (HTTP 429, 502, 503, 504, retryable transport errors/timeouts, and lost acknowledgements). Use the existing production transfer/reconciliation machinery and a shared retry policy where compatible; integrate Laboratory and ordinary save paths without creating parallel transfer engines. Before retrying any potentially committed write, reconcile its stable operation ID, exact destination key, expected identity and available production receipt/remote evidence. Retry only when safe; unresolved publication remains uncertain rather than blindly writing again. Never replay a confirmed publication or overwrite unrelated objects.
- Use bounded attempts, exponential backoff with jitter, provider Retry-After where applicable, and the existing authorization, execution, per-file, request, cost, disk and audit budgets. Reserve sufficient time/resources for final reconciliation and audit. Revisit eligible failed operations automatically before campaign finalization; do not require manual continuation for recoverable errors while an authorized window and budget remain. Avoid retry storms, indefinite loops and unnecessary blocking of healthy queue items. Permanent validation, permissions, cancellation, revoked/expired authorization, and genuine storage exhaustion must remain actionable and must not trigger unauthorized retries.
- Preserve one logical operation identity and immutable source/destination intent across attempts. Record every attempt, classification, delay, reconciliation, outcome, and exhaustion reason durably; distinguish attempts from unique confirmed files, initial failures from final failures, and recovered operations from unresolved ones. Retries must never double-charge free allowances or duplicate Queue/History success records. Report benchmark results at the actual cutoff without retroactively moving completions into the window. Keep automatic local receipts available even on interruption.
- P0 deterministic regression: reproduce a 555-file campaign with one injected recoverable 502 (including a case before publication and a separate lost-acknowledgement case after publication). Require 555/555 unique verified publications, 555 exact independent location matches, zero unexplained missing/extra/duplicate keys, no replay of confirmed writes, zero staging leftovers and correct usage accounting, with no manual intervention and within the configured test grant/budgets. Also exercise 429/Retry-After, repeated 5xx until exhaustion, connection loss, uncertain publication, permission failures, cancellation, expiry, process restart, and no available retry budget. Preserve the distinction between local fixture evidence and live Windows/Cloudflare acceptance; provide reproducible scripts and redacted receipts. Reuse the newer Laboratory baseline referenced above; report dependency gaps explicitly.
- P1 (only after P0 correctness): detailed aggregate recovery metrics and configurable adaptive concurrency. Keep the existing stable single-slot default unless separately validated; do not trade correctness, cleanup, or authorization enforcement for speed. Defer unrelated throughput tuning if necessary.
