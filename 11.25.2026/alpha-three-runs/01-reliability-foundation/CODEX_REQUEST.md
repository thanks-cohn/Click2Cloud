## Architecture and non-negotiable invariants
- Extend the existing production operation/outcome records, Queue stores and Lab journal rather than replacing them or introducing another transfer engine. Establish the authoritative logical outcome and its evidence once per operation; Queue, History, receipts, accounting and Lab consume it via narrow existing or compatible interfaces. Distinct durable stores may serve different purposes; explicitly reconcile them, with idempotent projections and checkpoint/replay rules rather than pretending separate storage systems share an atomic transaction.
- One permanent logical operation ID; separate subordinate attempt IDs and batch/child IDs. Immutable account/provider, source identity, destination and intent. Persist intent and authorization binding before dispatch, and durable commit-request/acknowledgement/verification transitions at the existing appropriate boundaries. Never infer remote or local completion from request acceptance. Prevent concurrent owners from dispatching the same logical attempt; recover abandoned claims safely. Never weaken existing reconciliation or scope checks to permit a retry.
- A confirmed publication is never blindly replayed; a partial or uncertain operation is never Verified; a retry never creates a second success card or allowance deduction; History preferences and preview generation never affect transfer correctness, Queue, authorization, receipts or recovery. No new remote operations after expiry/revocation; already in-flight outcomes can remain uncertain. Keep local evidence accessible without cloud authentication.
- Standardize a small error/outcome taxonomy using existing codes where possible: retryable transient, throttled, auth required, revoked, conflict, storage exhausted, permanent failure, cancelled, uncertain publication, and verified success. Preserve original typed provider errors and evidence. Provider adapters declare capabilities rather than assume R2 semantics; no speculative universal framework.
- Inspect existing licensing, usage accounting and activation interfaces early; define the minimal stable admission/reservation/outcome hooks and idempotent operation keys for Run 2 continuity and Run 3 entitlement integration. Preserve current production policy, including paid behavior; do not introduce download charges, reset allowances, change pricing/period/count, or implement payment/cloud continuity here. Test hooks with isolated synthetic fixtures, never a production-accessible quota bypass. Document unresolved policy or external dependencies early.
- Protect extension ID/OAuth callback, existing native wire/API compatibility, existing R2 staging/conditional publication, ordinary durable upload flow, menu modes, screenshots/shortcuts, previews, archive modes, Queue/History, settings/destinations and old Lab commands. Use versioned additive migrations, compatible readers and non-destructive recovery for existing journals, receipts, settings and queued jobs; document tested rollback limits and avoid destructive downgrade promises. Establish baseline test/build evidence, including the known 869/870 JS baseline failure and Windows-only skips, and compare resource usage where measured.

## Reasons — why these choices belong in Run 1
- Pinning the proven Laboratory baseline and deferring Onyx visual transplantation protects existing engineering assets and avoids a costly branch merge.
- Durable state before retries gives both directions and later provider adapters a common recovery contract; stable IDs and bounded scheduling prevent duplicate publication, duplicate accounting and retry storms.
- Background-owned downloads and explicit local publication evidence prevent a UI lifetime or a request acknowledgement from masquerading as successful completion.
- Independent read-only download admission and reopened disk verification give Run 2 a trustworthy, reusable harness, rather than four independent testing engines.
- Early identity/accounting/entitlement interface discovery reduces Run 2/3 coupling and exposes commercial dependencies without building commerce prematurely.
- Derived History aggregates, stable thumbnail selection and independent receipt preferences keep the customer interface light without losing evidence or burdening transfer execution.
- Backward compatibility, protected regressions and explicit verification levels preserve existing users and distinguish a good fixture from a real-provider pass.
- Timeboxed coherent slices and a precise handoff maximize useful inherited work rather than rewarding superficial feature counts.
