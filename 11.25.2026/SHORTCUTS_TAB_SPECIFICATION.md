# ReDown — Shortcuts Tab Specification

Owner-approved interaction direction, November 27, 2026
Reference: MY_INTENDED_IMPLEMENTATION.md and the approved interactive Shortcuts tab prototype. Part 2 establishes shared contracts and safe migration; Part 3 implements the actual UI and all-provider screenshot/chord-click workflows. This document controls the new shortcut destination selectors and supersedes earlier proposals to expose extra basic-cloud destination modes in those selectors. Preserve existing reliability, authorization, usage, scope and release requirements.

## 1. Intent and visual structure

Extend the working ReDown experience rather than redesign the application. A dedicated Shortcuts tab in the existing navigation gives customers direct control over Shortcut + Click routes and ordinary configurable Explorer/History assignments. Screenshots remains a separate page. Reuse the existing theme/Aesthetic API and shelf layout, including Onyx; the approved prototype is a layout reference, not literal production CSS, hardcoded data or proof of functionality.

In top-to-bottom order:
- Shortcuts heading.
- Shortcut + Click: saved binding rows showing key, provider and location; a simple Add shortcut control and inline editor. On the empty first visit, showing the inline editor immediately is acceptable and matches the approved prototype. One short instruction: Hold your shortcut and click an image to save. Do not force a configuration or tutorial.
- Explorer & History: existing History, Open Explorer search, Focus filename search and optional Divider cycle. Divider cycle is unassigned by default. Keep the current settings choice for divider behavior.
- Collapsible Built-in controls: retained copy/paste, select all, selection, navigation, open/dismiss, delete and relevant context-specific controls.
- Existing shared footer, scroll and navigation behavior. No extra permanent status footer, fake online indicator or prototype text in production.

Use clean compact rows, subtle separators, existing minimal underline dropdown styling, readable labels and theme-aware focus states. No nested bulky cards, unnecessary dialogs, page overlay or forced shelf opening. Editor labels: Shortcut, Provider, Location (basic clouds) or Bucket and Directory (R2), plus Cancel and Save. Show account selector only where needed to disambiguate authorized accounts. Preserve accessibility, narrow shelf layout, keyboard focus and scrolling; use existing accessible controls rather than new custom dropdown framework.

**Page separation (owner-approved):** Screenshots remains its own separate existing page. All screenshot shortcut assignments, provider/location controls, screenshot rules, capture settings and Screenshot Manifest controls belong exclusively on Screenshots. Do not display screenshot rows, editors or a duplicate Screenshots section in the Shortcuts tab. Shortcuts contains Shortcut + Click, configurable Explorer & History assignments and retained built-in controls only. Both pages use the same canonical shortcut registry, available-choice filtering, conflict validation and persistence; a key is excluded only for an actual conflicting effective input scope/trigger, not merely because it exists on another page or unrelated domain; manual conflicts identify the actual existing action/target and website scope even across pages. Cross-page conflict resolution is not a second screenshot editor. Preserve existing navigation, the two-choice basic-cloud location policy and silent same-account fallback.

## 2. Exact provider and destination controls

Provider choices: Cloudflare R2, Google Drive, OneDrive, Dropbox; list actual connected/eligible accounts and explain unavailable connection where relevant. Do not manufacture accounts, buckets or directories. Selecting a provider determines the displayed fields.

| Provider | Location controls for a newly configured screenshot or chord-click binding |
|---|---|
| Google Drive | ReDown folder / Account default |
| OneDrive | ReDown folder / Account default |
| Dropbox | ReDown folder / Account default |
| Cloudflare R2 | Existing authorized bucket selector and existing directory/prefix controls |

For all three basic providers, the Location dropdown has EXACTLY TWO choices: ReDown folder and Account default. No third Original cloud location option, no separate Existing folder/custom folder option, no directory text field or folder picker in this new binding editor. Same choices in both shortcut and screenshot destination configuration. Do not introduce an arbitrary folder creation workflow. On R2 use the existing working setup, including root/prefix and applicable rule behavior; do not flatten or replace it.

ReDown folder explicitly requests the standard visible redown folder for the selected authorized account. Account default uses the selected account's existing approved default resolver (including applicable rules and opt-out/original behavior as defined in Part 2); it is not a separate new root selector. Keep account identity explicit when multiple accounts exist; do not silently use another account.

This is a simplification of the screenshot/chord configuration UI, not a prohibition on existing explicit Save Here/manual Explorer destinations or internal canonical target descriptors. Preserve unrelated file operations and existing R2 destinations. If an older authorized basic-cloud binding or imported manifest contains a legacy explicit root/custom target that cannot be represented by the two new choices, preserve the original stored intent and explain its existing destination without silently mapping it to a different target. Require a deliberate user choice of one of the two modes to replace that legacy intent; unresolved imports must be explicit and must not dispatch to guessed targets. Do not offer root/custom as extra choices in a new binding editor. Inspect real predecessor data before deciding whether any such legacy records exist.

## 3. Mandatory silent fallback — done and done

For a basic-cloud ReDown folder binding, if a verified usable redown folder is already ready, save there. Otherwise immediately start saving to the selected account's authorized default/original save destination, using the existing Part 2 same-account fallback resolver. Do not wait for folder discovery, creation, a retry or verification. If the account's configured default itself normally uses redown, resolve its authorized original location without recursively retrying redown. Do not reroute to another provider/account or unrelated arbitrary target.

Independently prepare/reuse redown with bounded lifecycle-triggered work. If it cannot be created, is denied, deleted, ambiguous, conflicting, times out, or its creation acknowledgement is uncertain, the ordinary save simply uses that account's default/original location. No warning, confirmation, fallback toast, popup, forced repair, wait or extra customer step. Normal verified completion feedback is unchanged. Record the actual destination in the operation receipt and History. If default/original is not authorized or the actual file transfer fails, present the existing truthful actionable error; no bypass and no false success.

Once redown becomes verified ready, only new operations whose resolved intent selects redown switch to it. Do not move old files. If a previously verified redown folder becomes unusable during dispatch, fallback is allowed only when nonpublication is established per the Part 2 frozen-operation/batch contract. An uncertain file publication is not permission to create a second copy. Independently recover/reconcile the original operation. Account-default bindings follow existing account preferences and rules. Explicit redown binding takes precedence over applicable rules; fallback changes only the unavailable standard folder, not the chosen account, feature allowance group or source.

Explicit ReDown-folder selection for an individual screenshot/chord binding overrides the account's ordinary destination opt-out only for that binding. Standard redown infrastructure preparation independently runs for both account destination modes; opting out changes ordinary file routing only. Respect explicit metadata removal, revocation and read-only scopes. Account-default mode evaluates only applicable rules compatible with the chosen authorized account, then its configured preference/legacy resolver. A failed explicit redown preparation uses the same account's authorized default/original destination, bypassing unavailable redown without recursion; do not use another account, cross-provider rule or arbitrary alternative. Folder creation uncertainty is not file publication uncertainty: only proven nonpublication permits changing an already admitted write target. No fallback notice.

## 4. Shortcut choices and conflicts

One canonical registry feeds every available-shortcut dropdown (screenshots, held chords, configurable Explorer/History). Show only actually eligible unoccupied candidates for the relevant action, trigger and scope; keep the row's own current assignment visible while editing. Recompute after saved changes, actual browser registration changes, relevant layout/scope changes, disable/remove or release. Do not hardcode the prototype's illustrative candidate pool. Respect Chrome/OS reserved shortcuts, AltGr/layout, protected editing, supported command slots and overlapping two-/three-key held chords. Ordinary browsing and typing must remain normal.

Provide Custom… to enter a supported combination. If it conflicts in the effective scope, show the existing assignment/action, website scope and target plus the requested action/target. Reuse on nonoverlapping domains is valid. Offer Keep existing (cancel conflicting change), Override (old assignment becomes unassigned), or Change existing shortcut (choose another eligible free key). One Save applies the chosen changes together after validating the complete proposed configuration; Cancel changes nothing. No duplicate active dispatch or pre-Save override. If registration/persistence fails, preserve or restore previous working state where possible and show actual browser constraints. For Chrome-managed assignments that require chrome://extensions/shortcuts, expose the real required action and confirm actual registration; do not claim arbitrary dynamic registration. The ordinary available-dropdown path should not invoke a conflict dialog.

Retained defaults: Alt+Q and Ctrl+Shift+Y screenshots; Alt+Shift+H Shelf/History; Alt+Shift+F open Explorer search; Ctrl+Shift+F7 local filename search. Keep Ctrl+C/V/A, Delete, Enter, Escape, filename selection, navigation, selection modifiers, column and preview controls and zoom. Release Ctrl+Shift+F9, Ctrl+X, Shift+F10, Ctrl+Shift+N, F2, F5 and Backspace as inherited ReDown assignments. Additional refresh remains unassigned. Keep underlying actions for the other six; remove the cloud-file Cut feature entirely (per MY_INTENDED_IMPLEMENTATION.md), preserving ordinary text editing, Copy/Paste, direct Move and supported drag/drop. Do not reintroduce released defaults through Restore Defaults. Retain legitimate unrelated customizations, use safe migration, no claim that released keys are necessarily available in Chrome. Keep the Menu key where supported and ensure context menu is keyboard-accessible even on keyboards without it.

Keep fixed navigation/editing/accessibility controls protected: release-all and Override affect only eligible configurable ReDown bindings, never native browser/OS shortcuts or fixed controls. Default screenshot/History/search assignments are retained but configurable only through supported mechanisms. For browser-managed conflicts, stage the intended change, require the actual Chrome shortcut-settings action if necessary, re-read actual registration before committing effective assignments; Cancel before external changes leaves settings intact, and after an external change report/reconcile actual state rather than promise a rollback Chrome cannot perform. Unverified or reserved keys are not advertised as freely available. Keep Screenshots separate; cross-page conflict summary may identify/reassign a conflicting key without duplicating screenshot destination configuration. Retain an accessible item-menu entry point for keyboards without Menu and a direct divider-cycle control in existing Settings if needed to invoke the cycle without a key; reuse existing actions.

## 5. Configuration and runtime

One setup for each independent route:
1. Choose or enter an eligible shortcut.
2. Select provider/account.
3. Choose one of the supported destination controls above.
4. Save.

Rows can be added, edited, disabled or removed using existing direct UI conventions; existing configured row shows actual key and destination, unassigned is truthful. Save validates current scope, binding revision and selected destination. Editing/cancelling cannot alter any admitted transfer. Use versioned stable binding IDs and shared settings persistence; no competing store. Reuse shared configuration/manifest operations and canonical resolver. No credential export. Do not implicitly perform a capture or file write while configuring or importing.

Screenshot: reuse the existing R2 capture path as reference; provider-neutral captured bytes enter the same authorized production save engine for all four clouds. Preserve capture gesture, permissions, rate limits and selected current tab. No deferred capture of a different tab.
Shortcut + Click: hold two or three configured keys, deliberately primary-click an eligible item, submit exactly one logical operation through existing shared save path. Stay armed for distinct eligible clicks while held; disarm on release, focus/visibility loss, navigation, tab/window/frame change or cancellation. No duplicate event bubbling, auto-repeat dispatch, synthetic-page-event bypass, arbitrary key logging or broad new permissions. No interception of ordinary editing or unarmed clicks. Verify source, sender, scope, provider/account and frozen destination. Preserve queue, retries, existing normal feedback, one verified receipt and exactly one allowance settlement for successful logical save. No new transfer engine.

## Mandatory Chrome-first compatibility and evidence gate (owner direction, November 27, 2026)

Build around supported Chrome behavior, not speculative workarounds. Official platform documentation plus measured packaged-browser behavior governs every offered key, action, scope and capability. A valid registry entry, manifest declaration, synthetic event, or API dispatch is not proof that an actual shortcut is usable. Preserve the existing four suggested defaults and stable command IDs where verified; never silently replace a user's working assignment. Reference current official documentation before implementation and at qualification:

- Content scripts: https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts

### Three supported input paths, one action registry
1. Chrome-managed commands: declarations belong in the manifest; at most four developer-suggested shortcut defaults. Additional commands may be declared unbound and assigned by the user through chrome://extensions/shortcuts. Use documented key syntax and platform modifiers; Ctrl+Alt is not a supported Commands combination, and Chrome/OS-reserved shortcuts win. Inspect actual supported methods (getAll/onCommand); do not implement a nonexistent arbitrary setter, rewrite profile preferences, simulate assignment, or silently switch to Global. Default to In Chrome; Global is not necessary for V1. Re-read actual registration on opening settings, focus return and relevant lifecycle changes; requested versus actual assignment is explicit. No per-save setup or polling. A staged assignment is not active until registration is verified; if an external change cannot be rolled back, report and reconcile actual state.
2. Page-held Shortcut + Click: use narrow authorized content-script scope and actual delivered keydown/keyup/click events, not Chrome Commands as held-state input. Only offer combinations verified for their intended supported contexts; keep state document/tab/frame scoped and disarm on lifecycle/focus/permission changes. No raw keystroke logging, password/editable-field interception, OS-wide listener, restricted-page injection, browser reservation bypass or new blanket host permissions for shortcut capacity. Unsupported contexts retain existing authorized right-click/manual alternatives, not false promises of global coverage. Scope and failure isolation must preserve other bindings.
3. Local interface: contextual Explorer/History/shelf controls use existing focused UI handlers and the same canonical registry, independently of manifest command count. Keep protected navigation, accessibility and normal editing. Do not advertise these as browser-wide commands.

## Contextual shortcuts — implementation completeness contract (mandatory, source-reviewed)

This section resolves implementation choices in the approved contextual design; it is not another feature or engine. The customer-facing workflow must be complete on the first accepted Alpha build, not merely an API, a settings prototype, or an installed listener.

### Source baseline and decided implementation

Inspected at continuation commit 154b208de819b1dce189e68d8abd4c7d82fb0399 (runtime 0.3.32.5):
- extension/manifest.json has four suggested commands, existing broad HTTP/HTTPS host_permissions and static all-frame projectile/console feedback scripts, no scripting permission and no optional_host_permissions declaration. scripts/build-extension.mjs copies this manifest to the package. Site selection is therefore NOT equivalent to Chrome permission, and a new prompt may not appear when Chrome already grants access. Do not advertise the current extension as having only selected-site host access.
- src/api/shortcuts.mjs uses commandShortcutBindings version 1, command-ID-to-chord overrides, serialized local writes, global duplicate rejection, and fallback to defaults when loaded keys collide. Extend/migrate this existing authority into revisioned scoped binding records; do not preserve the global duplicate test or whole-config reset for contextual records. Keep adapters for existing local actions and actual Chrome command readback.
- extension/shortcut-settings.mjs installs focused document keydown handling and displays Chrome assignments; src/chrome/command-bindings.mjs reads getAll and opens Chrome's shortcut settings. extension/background.mjs dispatches Chrome onCommand, and extension/screenshot-background.mjs handles screenshot commands. extension/projectile.js handles right-click animation context, not a general shortcut recognizer. src/chrome/provider-panel.mjs wraps actual sidePanel.open, which can fail if gesture authority is lost. Reuse these mechanisms; do not infer a contextual workflow exists from them.
- Use a narrowly registered isolated-world top-frame contextual content script with the documented chrome.scripting registration/reconciliation path (add the necessary scripting permission only after recording why, preserving existing required permissions and extension ID). Keep one script implementation, one registration per effective nonduplicative scope set, and one per-document listener instance. Existing feedback scripts are not a license to listen for shortcuts on every website. Use actual getRegisteredContentScripts/readback and event-based repair on install/update, startup, settings or permission change; persist registrations where supported. Reconcile already-open permitted tabs once on enable using supported injection, with idempotent document guard; if not possible, explicitly show refresh required, never say enabled and silently ignore input.
