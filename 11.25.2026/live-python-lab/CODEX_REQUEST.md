## Mandatory manifest-first workload contract
The laboratory runner is a general manifest interpreter, not a collection of hard-coded workload scripts. A versioned, human-editable JSON manifest is the authority for what to generate, where to read/write, which operations to perform, in what order or concurrency, and what to verify. Provide a JSON Schema, checked-in sample manifests for Quick, Everyday, Comprehensive, Heavy, Endurance, and Custom, a validator/dry-run, and a stable Windows CMD entry point accepting a manifest path (e.g. --manifest PATH). Profile names are convenient manifest selections, not separate implementations.
- Manifest fields: schema version, workload identity, deterministic seed and fixture generator version; per-fixture ID, valid media/document format, exact integer sizeBytes or explicit size range with deterministic resolution, count, naming and relative folder layout, source kind (generated or approved local corpus), local source/destination roots and logical remote target aliases; per-phase operations, dependencies, direction, concurrency, cycles, timeouts, failure injection/recovery policy and verification expectations; hard limits for files, total bytes, transfer/verification traffic, temporary disk, provider requests, time and approved cost.
- Remote location fields resolve only within a separately authorized provider/account/bucket and exclusive run prefix. Treat manifests as untrusted input; reject traversal, scope escapes, unsafe aliases, unauthorized mutations, over-budget plans, unsupported sizes and duplicate IDs before dispatch. A manifest never grants authorization or contains credentials, tokens, absolute private paths or historical live object identities in checked-in examples. Runtime-local overrides are allowed only within owner-approved scope and recorded in the resolved plan.
- Resolve and freeze a concrete run manifest before any writes: deterministic filenames, exact sizes, SHA-256 source inventory, selected destination keys, operation IDs, actual fixture generator identity and effective budgets. Retain original manifest, canonical resolved-manifest digest, commit/SDK/engine versions, per-operation results and independent remote/download hashes in every run's evidence. Compare runs using stable fixture and scenario IDs and explicitly report changed parameters; never overwrite prior evidence or silently regenerate a changed source on resume.
- Include a draft heavy manifest with 20 distinct 100,000,000-byte valid media upload fixtures, 20 distinct preseeded verified download fixtures, upload-only, download-only and bidirectional phases, and explicit accounting for seeding, readback, repetition and cleanup. The 40-way phase must prove overlapping active byte transfers. Include an everyday manifest with mixed ordinary formats, sizes, nested paths and operation sequences. Future larger-file workloads (e.g. sizeBytes=1000000000 for 1 GB) and altered counts/concurrency/locations must be expressible by editing the manifest alone, subject to supported format generation and validated provider/resource limits; no silent downscaling or code edits to change workload parameters. Unsupported capability is an explicit BLOCKED/UNSUPPORTED result, not a PASS. Do not promise future size support merely because a manifest can express it.
- Keep manifest parser, fixture generation, planner, scheduler, transport, verification and reporting modular. Add focused tests for schema validation, deterministic resolution, reproducibility, parameter changes, scope and budget rejection, and resume with a mismatched manifest digest. Heavy live execution is owner-run only. Document how to create, validate, run, compare and archive manifests. Do not build a manifest editor into Settings; keep the single laboratory card unchanged.
